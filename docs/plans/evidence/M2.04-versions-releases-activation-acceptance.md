## Accepted contract implemented

The migration follows the M2.02 frozen order in one transaction:

1. create account/Managed-Skill-scoped immutable `private.managed_skill_versions`;
2. create same-scope `private.managed_skill_releases`, with M1.06 lifecycle authority only on the release binding;
3. add nullable `private.managed_skills.active_release_id` and nonnegative `activation_revision` only after both child authorities exist;
4. add the same-account/same-skill active-release foreign key, durable activation receipts, and the ungranted CAS implementation/API.

Version identity and content coordinates are immutable. Exact canonical manifest bytes are `bytea`, so PostgreSQL cannot parse or reserialize the M1.03 projection. Both manifest and content digests use the checked `sha256:` grammar. Same-skill manifest/content coordinates are unique, while equal content across different Managed Skills/accounts is allowed.

Release bindings use the exact nine-state M1.06 live vocabulary. The trigger enforces the legal transition graph and prevents an actively selected release from becoming non-active, denied, or revoked before its pointer is removed. Eligibility reasons use a bounded, sorted, duplicate-free canonical code grammar; no unfrozen closed reason vocabulary was invented.

Activation derives the account from `auth.uid()`, accepts no account argument, takes the account advisory lock before Managed Skill/version/release row locks, validates expected revision and same-scope eligibility, increments revision once per pointer change, stores a scoped durable receipt, replays exact input without mutation, rejects conflicting key reuse, and treats rollback as selection of another already-eligible release without version mutation.

All new tables force RLS. No new policy exists. Direct table access and the exact API function remain ungranted to `public`, `anon`, `authenticated`, and `service_role`. Existing catalog `current_version_id` authority is untouched.

## Phase-local owner constraint

The accepted M2.02 conventions require both forced RLS with zero M2.04 policies and a future NOLOGIN vault definer. A NOLOGIN/non-BYPASSRLS function owner cannot execute through forced RLS while zero policies exist. The first implementation also proved that the local migration principal cannot transfer ownership to `skillmap_vault_definer` without temporary role membership.

Therefore the two ungranted activation functions remain owned by the local migration `postgres` role for M2.04. They are inert to application roles. M2.10 MUST, in the same transaction that adds the exact owner policies and reviewed execute grant, transfer both function owners to `skillmap_vault_definer`; no grant may precede that transfer. This is a bounded phase-local dependency, not public behavior.

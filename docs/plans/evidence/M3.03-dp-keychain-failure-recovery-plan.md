## Recovery design: bounded attribute-only enumeration and exact deletion

### Reserved namespace and exact shapes

The proof owns exactly two service namespaces and one account shape:

| Row | Service format | Exact length | Account format | Exact length |
|---|---|---:|---|---:|
| unsigned | `^skillmap-m303-dp-unsigned-[0-9a-f]{24}$` | 50 | `^synthetic-[0-9a-f]{24}$` | 34 |
| `adhoc` | `^skillmap-m303-dp-adhoc-[0-9a-f]{24}$` | 47 | `^synthetic-[0-9a-f]{24}$` | 34 |

The recovery source must contain both literal prefixes and reject every other
prefix, case, suffix length, Unicode normalization, control character, or
non-string attribute. A row may have zero or one candidate. More than one
candidate for either row, more than two total, duplicate service/account
values, or a cross-row prefix mismatch is ambiguous and forbids deletion.

The ad-hoc namespace is scanned even though the retained receipt shows that
only the unsigned row launched. This is namespace hygiene for earlier
proof-only attempts, not a claim that the retained run reached ad-hoc. The
strict one-per-row cap prevents a broad historical purge.

### Versioned candidate fingerprints and manifest

The only allowed receipt `row` values are the exact ASCII strings `unsigned`
and `adhoc`; `ad-hoc`, case variants, or any other spelling are invalid.

For each bounded candidate, compute `pair_fingerprint` as the SHA-256 digest of
these exact bytes:

```text
UTF8("skillmap.m3-03.recovery-pair.v1\0" + row + "\0" + service + "\0" + account)
```

Encode the digest as exactly 64 lowercase ASCII hexadecimal characters with no
`sha256:` prefix. Comparison is exact over the lowercase bytes. The fixed
domain separator includes the terminating NUL shown above; every other `\0` is
one literal zero byte, not the two printable characters backslash and zero.

Order candidates by fixed row rank (`unsigned` first, `adhoc` second), then by
raw ASCII service bytes, then raw ASCII account bytes. With the one-per-row cap,
the latter keys are still specified to prevent implementation-dependent order.
Compute `candidate_manifest_digest` as the SHA-256 digest of:

```text
UTF8("skillmap.m3-03.recovery-manifest.v1\0" + decimal_candidate_count + "\0" + ordered_pair_fingerprints_joined_with_LF)
```

Encode that digest as exactly 64 lowercase hexadecimal characters with no
prefix. `decimal_candidate_count` is canonical base-10 with no sign or leading
zero except `0`; the join delimiter is one LF byte and there is no trailing LF.
For zero candidates the digested suffix is exactly `0\0`.

The dry-run receipt records row counts, ordered fingerprints, and this manifest
digest, but never service, account, or access group. A later enumeration must
recompute the same count, order, fingerprints, and manifest digest before any
delete is reachable.

### Ephemeral full-composite authority manifest

The pair fingerprints above are redacted review evidence, not deletion
authority. For every dry-run candidate, the helper must also retain the full
exact composite tuple in one ephemeral authority manifest. The manifest is the
following deterministic byte sequence; `||` means byte concatenation and
`NUL` means one `0x00` byte:

```text
UTF8("skillmap.m3-03.recovery-authority-manifest.v1") || NUL ||
UTF8(decimal_candidate_count) || NUL ||
for each candidate in canonical order:
  UTF8(row) || NUL ||
  UTF8(service) || NUL ||
  UTF8(account) || NUL ||
  UTF8(access_group_kind) || NUL ||
  UTF8(access_group_value) || NUL
```

The class, Data Protection Keychain selector, accessibility, and
synchronizable value are fixed plan-wide constants checked for every entry;
the serialized fields are the complete candidate-varying deletion authority.

Canonical candidate order is fixed row rank (`unsigned`, then `adhoc`), then
raw UTF-8 service bytes, raw UTF-8 account bytes, access-group-kind rank
(`none`, then `present`), and raw UTF-8 access-group-value bytes. The field
order inside each entry is always row, service, account, access-group kind,
access-group value. The count uses the same canonical decimal encoding as the
redacted candidate manifest. There is a final NUL after every entry and no
other prefix, length field, newline, BOM, JSON escaping, or trailing byte. A
zero-candidate authority manifest is exactly the schema bytes, NUL, `0`, NUL.

`access_group_kind` is exactly ASCII `none` or `present`. No returned access
group is encoded as `none`, NUL, empty value, NUL. A returned non-empty string
is encoded as `present`, NUL, its exact value, NUL. Thus absent and empty are
not conflated: an empty returned string is malformed, while `none` truthfully
records that the attribute was absent and makes the dry-run
`DRY_RUN_BLOCKED`. Neither state can silently substitute for the other.

`row`, service, and account are already restricted to the exact ASCII shapes
above. A present access-group CFString is converted losslessly to UTF-8 from
its exact Unicode scalar sequence; do not normalize, case-fold, trim, or
replace characters. Reject a value that cannot be encoded losslessly, is
empty, contains U+0000, or exceeds 1,024 UTF-8 bytes. Comparisons are over the
resulting bytes, not locale-aware strings.

Write exactly those bytes to an ordinary, non-symlink file created with
exclusive/no-follow semantics inside the run-owned `0700` directory, owned by
the current non-root UID, mode `0600`, then fsync the file and directory. The
file is immutable after the dry-run receipt is finalized and, for a nonzero
inventory, must remain available until the accepted validity window expires,
including after a partial or complete cleanup attempt. Its path and bytes are
never durable repository evidence.

Compute `authority_manifest_sha256` over the complete file bytes and encode it
as 64 lowercase hexadecimal characters without a prefix. The durable redacted
dry-run receipt binds that digest but contains no exact service, account,
access-group kind/value, manifest path, boot identifier, or audit-session ID.
An independent reviewer may hash the protected file and check its structure
without printing or copying its candidate-bearing bytes.

### Enumeration query

Build the same reviewed recovery Swift source as actually unsigned and ad-hoc
executables. Each executable may act only on the matching row prefix. Before
any query, prove the expected signature state, no Team ID, no entitlements, no
embedded profile, no access-group entitlement, non-root execution, matching
real/effective UID, and a run-owned `0700` temp directory.

Each binary issues one non-interactive `SecItemCopyMatching` query with:

- `kSecClass = kSecClassGenericPassword`;
- `kSecUseDataProtectionKeychain = true`;
- `kSecAttrAccessible = kSecAttrAccessibleWhenUnlockedThisDeviceOnly`;
- `kSecAttrSynchronizable = false`;
- `kSecMatchLimit = kSecMatchLimitAll`;
- `kSecReturnAttributes = true`;
- no data, transient-reference, or persistent-reference return request; and
- an `LAContext` with interaction disabled, supplied through
  `kSecUseAuthenticationContext`.

`kSecUseAuthenticationUIFail` is deprecated in current Apple documentation;
the non-interactive `LAContext` path is required. No prompt is acceptable.

The returned attribute dictionaries remain in private process memory. The
helper extracts only service, account, accessibility, synchronizable state,
and access group for a candidate whose full service and account pass the exact
formats above. It must not serialize, hash, count, log, print, or retain any
attribute of a non-candidate. It must never request `kSecReturnData` or emit a
password value, generic attribute, label, creator, date, path, or access group
to stdout, stderr, argv, environment, or durable evidence. Candidate composite
bytes may exist only in private process memory and the protected authority
manifest defined above.

`errSecItemNotFound` means zero visible candidates for that binary. Any other
non-success status, locked/interacting state, unexpected result type, or
malformed candidate attribute is a fail-closed blocker and performs no
deletion. An absent candidate access group is serialized explicitly as `none`
before producing the same blocked outcome. A zero result proves absence only
if both expected binary forms complete the query on the same non-root macOS user and
an independent Luna reviewer repeats the zero scan. If the platform prevents
that proof, residue remains unknown.

### Dual-clock, boot UUID, and macOS audit-session validity binding

At authority-manifest finalization, sample all of the following before writing
the durable dry-run receipt:

- `observed_at_wall_ns`: Unix-epoch nanoseconds from `clock_gettime` with
  `CLOCK_REALTIME`;
- `expires_at_wall_ns = observed_at_wall_ns + 900000000000`;
- `observed_at_monotonic_ns`: nanoseconds from `mach_continuous_time()` using
  the current `mach_timebase_info` conversion;
- `expires_at_monotonic_ns = observed_at_monotonic_ns + 900000000000`;
- the `kern.bootsessionuuid` value parsed as a UUID and rendered as exactly 36
  lowercase ASCII characters in `8-4-4-4-12` form with no braces; and
- the current task's positive macOS audit-session ID extracted from its kernel
  audit token under the API contract below.

All nonnegative integer fields use unsigned canonical decimal text with no sign
or leading zero except `0`, and overflow is a blocker. Serialize the accepted
positive `au_asid_t` as canonical base-10 ASCII with no sign or leading zero.
Hash the raw boot/audit-session identity as exactly:

```text
UTF8("skillmap.m3-03.recovery-boot-audit-session.v1\0" + canonical_boot_session_uuid + "\0" + decimal_audit_session_id)
```

The receipt retains only the resulting 64-character lowercase-hex
`boot_audit_session_context_sha256`, not the UUID or audit-session ID. The raw
identity, the four exact clock values, and the accepted authority-manifest path
are kept in the protected `0600` run record; the public receipt binds the clock
values, context digest, and `authority_manifest_sha256`.

#### Exact audit-session API and error contract

Use public macOS interfaces only:

1. Include `<mach/mach.h>`, `<mach/task_info.h>`, and `<bsm/libbsm.h>`.
2. Initialize an `audit_token_t`, set a
   `mach_msg_type_number_t` count to `TASK_AUDIT_TOKEN_COUNT`, and call
   `task_info(mach_task_self(), TASK_AUDIT_TOKEN, ...)` for the current task.
3. Require `kern_return_t == KERN_SUCCESS` and returned count exactly
   `TASK_AUDIT_TOKEN_COUNT`; any other return or count is
   `BLOCKED_AUDIT_SESSION_UNAVAILABLE` and makes deletion unreachable.
4. Pass the complete returned token by value to
   `audit_token_to_asid(audit_token_t)`, whose return type is `au_asid_t`.
   Never index or serialize `audit_token_t.val`; the SDK header requires BSM
   accessors because the token representation may change.
5. `au_asid_t` is a signed `pid_t` typedef. Require the extracted value to be
   greater than zero. Reject `AU_DEFAUDITSID` (`0`), `AU_ASSIGN_ASID` (`-1`),
   every other nonpositive value, or a value that cannot round-trip through the
   canonical decimal representation above as
   `BLOCKED_AUDIT_SESSION_INVALID`.

`audit_token_to_asid()` has no separate error channel, so the `task_info`
result/count and ASID range/sentinel checks are all mandatory. Do not use
`audit_session_self()` here: the current macOS SDK declares that Apple-private
API as returning a Mach audit-session port, not an `au_asid_t`. Do not call
`audit_session_join()` or otherwise change audit-session membership. The raw
token, Mach port, and ASID must never appear in argv, environment, stdout,
stderr, or durable evidence.

Pure and local integration tests must cover this boundary without changing the
operator's login state:

- injected `task_info` failure, short/long count, `0`, `-1`, and other
  nonpositive ASIDs all produce the exact blocked classes above and zero
  deletion-spy calls;
- three distinct helper processes, representing dry-run, independent reviewer,
  and recovery, each obtain their own current task audit token and emit only
  `boot_audit_session_context_sha256`; under the same current login audit
  session all three digests must be byte-identical;
- the test proves the three process IDs are distinct internally but does not
  retain a PID, raw token, ASID, or boot UUID; and
- injecting a different valid positive ASID with the same UID, boot UUID,
  clocks, receipt, and candidates must produce
  `BLOCKED_AUDIT_SESSION_CHANGED` before deletion is reachable. This exercises
  the value change a real logout/new login would expose; tests must not perform
  a logout or call an API that joins/creates an audit session.

The actual independent-review and later recovery commands must each recompute
the digest in their own process and compare it with the accepted dry-run
receipt. Unit injection is not a substitute for those process-bound runtime
checks. If separately launched Luna commands in the intended execution surface
do not share the dry-run ASID, stop with the blocker; do not weaken the gate or
join an audit session to make the test pass.

The authority is valid only while both clocks independently remain within
their inclusive observed/deadline bounds. Every sample must be greater than or
equal to the preceding sample from that same clock. Reject any wall-clock
rollback, monotonic rollback/reset, wall or monotonic expiry, changed boot UUID,
changed positive audit-session ASID, or boot/audit-session digest mismatch. A
reboot, logout/new login audit session, `task_info` failure, or separately
launched command with a different ASID can never inherit the old authority even
if wall time, UID, and receipt bytes otherwise match. Equality means the same
login audit session, not merely the same user account.

The raw dry-run receipt file SHA-256 is calculated after its final fsync and
represented as 64 lowercase hex characters without a prefix. For a nonzero
inventory, the exact two binaries, protected run record, and immutable `0600`
authority manifest remain in the run-owned `0700` temporary directory until
both wall and monotonic deadlines expire. They may then be removed only by a
run-owned, no-follow cleanup. No Keychain value or unrelated metadata is stored
there. A zero-candidate result may close recovery and remove that run-owned
temporary directory after independent acceptance because it carries no
candidate tuple or deletion authority.

An independent Luna High reviewer must accept the implementation diff, raw
receipt SHA, implementation and binary hashes, signature evidence, target/user
context, dual-clock/boot-UUID/audit-session validity, row counts, ordered pair
fingerprints, redacted manifest digest, and authority-manifest digest before
the coordinator may present a cleanup choice to the user.

### Receipt-bound deletion gates after explicit user authorization

If the independently accepted dry-run has zero candidates, close recovery and
do not invoke `--recover`. If it has one or two bounded candidates, stop. The
user must explicitly authorize deletion by naming the raw dry-run receipt SHA,
candidate count, ordered pair fingerprints, candidate-manifest digest, and
`authority_manifest_sha256`. Silence, “continue,” prior proof authorization,
or a receipt-independent approval is insufficient.

Only then may a later Luna High execution invoke `--recover`. The command must
require all of these explicit inputs:

```text
--dry-run-receipt-sha256 <64-lowercase-hex>
--authorized-candidate-count <1-or-2>
--authorized-candidate-manifest-sha256 <64-lowercase-hex>
--authorized-authority-manifest-sha256 <64-lowercase-hex>
```

Before deletion becomes reachable, `--recover` must:

1. load the fixed dry-run receipt path and verify its raw SHA exactly matches
   the authorized SHA and its status requires authorization;
2. verify independent Luna acceptance is recorded by the coordinator and the
   user authorization names that same SHA, count, fingerprint set, redacted
   manifest digest, and authority-manifest digest;
3. open the retained protected files with no-follow semantics; verify exact
   ownership/modes; hash the complete immutable authority manifest; and require
   its raw SHA to match the receipt, command, independent acceptance, and user
   authorization;
4. reuse the retained dry-run binaries and verify their exact hashes,
   signatures, source hashes, four-file implementation hashes, non-root user
   context, target OS/build, and protected run record match the accepted
   receipt;
5. re-enumerate both namespaces non-interactively and recompute the exact row
   counts, ordered pair fingerprints, and redacted manifest digest; serialize
   every returned full composite using the authority-manifest v1 rules and
   require the complete re-enumerated bytes to equal the retained accepted
   manifest byte for byte; and
6. sample both clocks, boot UUID, and audit-session identity, enforce every
   exact validity
   rule above, and abort without deletion on any added, removed, reordered,
   malformed, expired, rolled-back, restarted, audit-session-changed, or otherwise
   drifted fact.

Deletion proceeds in canonical manifest order. Immediately before each
individual `SecItemDelete`, the helper must perform this indivisible gate:

1. re-enumerate both namespaces and serialize the complete current
   full-composite inventory;
2. construct `expected_remaining_manifest` by applying the exact v1 serializer,
   including its recomputed count header, to accepted entries not already
   proven deleted in this invocation, and require the current manifest to equal
   those expected bytes byte for byte;
3. issue an exact attribute-only query for the next tuple, require cardinality
   one, and require the returned row/service/account/access-group representation
   to equal that accepted entry byte for byte;
4. resample wall time, `mach_continuous_time()`, boot UUID, and the current
   task-audit-token ASID through the exact API contract above; require both
   deadlines, monotonic non-decrease, wall non-decrease, and exact
   boot/audit-session equality; and
5. with no intervening await, subprocess, filesystem write, receipt update, or
   second Keychain operation, call `SecItemDelete` for that one accepted tuple.

Any expiry or composite/context drift aborts before that candidate's delete.
The exact delete query contains only class, service, account, access group,
`synchronizable=false`, accessibility, and Data Protection Keychain, with no
return keys. It is unreachable for an authority entry whose access-group kind
is `none`. After `errSecSuccess`, the same exact query must return
`errSecItemNotFound`, and a fresh full-composite inventory must equal the
expected accepted manifest suffix before the next item. After all candidates,
both namespace scans must return zero. A partial cleanup leaves the original
immutable authority manifest until expiry, writes only redacted progress, and
keeps the blocker for every unresolved entry.

The execution receipt binds the accepted dry-run raw SHA, authorized candidate
count, ordered fingerprints, manifest digest, source/binary/context hashes,
authority-manifest digest, dual-clock and boot/audit-session gate results,
re-enumeration evidence, per-item pre-delete check times, delete/post-delete
statuses, timing, and cleanup. It never retains exact identifiers, raw
boot UUID/audit-session identity, or unrelated metadata.

`BLOCKED_KEYCHAIN_RESIDUE_UNPROVEN`, retain the `0600` recovery record if one

## Future retry supervisor design

This design is contingent on a separate user authorization after independent
zero-residue acceptance. Nothing in the dry-run or optional cleanup authorizes
the retry.

### Record before native launch

For each retry run, generate a non-secret 128-bit lowercase-hex `run_id` and
fresh 256-bit nonce. Before either native binary launches, derive and persist
both exact service/account pairs in an atomically replaced JSON supervisor
record under a run-owned `0700` directory beneath the OS temporary directory.
The record must be an ordinary non-symlink file, owned by the current non-root
UID, opened with exclusive/no-follow semantics, mode `0600`, fsynced before
rename, and followed by a directory fsync.

Minimum record fields:

```text
schema, run_id, created_at, source_sha256, target_os_build,
row[unsigned|adhoc].service, row.account, row.access_group_state, row.state,
row.child_pid, row.deadline_ms, row.cleanup_state
```

Allowed row states are `prepared`, `launched`, `native_finished`,
`cleanup_started`, `clean`, and `blocked`. Exact identifiers are non-secret but
are cleanup authority and stay only in the protected run directory. Before
creation, `access_group_state` is exactly `not_yet_observed`, because no
candidate exists yet; this state can never authorize deletion. As soon as an
item is observable, the supervisor obtains its attributes through an exact,
non-interactive query and atomically writes the full row/service/account/
access-group tuple to a separate `0600` authority manifest using the same v1
serialization above. It then sets the JSON state to `present` and binds the
authority-manifest SHA. A returned absence is represented as `none` and blocks.
The record and manifest contain no nonce, value bytes, private key bytes,
environment, argv, username, hostname, or unrelated metadata.

The native child receives the nonce and row through a private inherited
channel or derives from a private inherited descriptor; exact identifiers must
not appear in argv, environment, stdout, or stderr. Cleanup reads the exact
pair from the pre-launch supervisor record and the exact access-group bytes
from the fsynced authority manifest, never from child output. If the child is
killed after creation but before the manifest transition, normal supervisor
control flow must perform the exact attribute-only query, fsync the completed
tuple, and only then attempt deletion. Failure to obtain and persist the full
composite blocks cleanup and every retry; it never permits a pair-only delete.

### Signal-aware and timeout-safe cleanup

Security-framework calls are not async-signal-safe. A signal handler must only
set an abort flag or wake a self-pipe. Normal supervisor control flow then:

1. stops launching new rows;
2. sends `SIGTERM` to the current child;
3. waits a fixed 500 ms grace period;
4. sends `SIGKILL` only if still running and waits until the child is reaped;
5. launches the dedicated cleanup binary using the already-fsynced record and
   authority manifest, with the same immediate full-composite and dual-clock/
   boot-UUID/audit-session gate before each delete;
6. runs exact post-delete and namespace-zero checks; and
7. exits with the original signal semantics after the receipt is fsynced.

Handle `SIGINT`, `SIGTERM`, and `SIGHUP` this way. No process can handle its own
`SIGKILL`, power loss, or whole-process-group destruction. For those cases, the
persisted record is the recovery mechanism: every later retry begins by finding
and resolving any non-`clean` supervisor record before creating a new canary.

Each native lifecycle has a 15,000 ms monotonic deadline. Receipt evidence must
distinguish `deadline_fired`, `SIGTERM_sent_at_ms`, `SIGKILL_sent_at_ms`,
`reaped_at_ms`, external signal, exit code, and child-reported result. A child
signal or missing result is an invalid run, not a capability verdict. Cleanup
gets a separate 15,000 ms deadline; its failure blocks all retry.

The supervisor record is removed only after the redacted durable receipt is
fsynced, exact post-delete checks pass for both rows, both reserved namespace
scans are zero, and the independent validator has enough receipt evidence to
repeat the scan. A candidate-bearing authority manifest remains immutable in
its protected directory until its bound wall and monotonic expiry even after a
successful delete; the supervisor may mark the row clean but must not erase or
rewrite those authority bytes early. On any cleanup uncertainty, keep both
protected files, return a redacted record locator based on `run_id`, and block.

### Retry outcome semantics

- `PASS_DP_KEYCHAIN_NO_PROFILE_CAPABILITY`: both unsigned and ad-hoc rows
  complete the full accepted lifecycle, every assertion passes, cleanup is
  proven, and independent Luna validation accepts.
- `FAIL_DP_KEYCHAIN_NO_PROFILE_CAPABILITY` with
  `failure_class=OBSERVED_CAPABILITY_FAILURE`: a native row returns a parsed
  known `OSStatus` or completes a failing capability assertion, and cleanup is
  proven. `errSecMissingEntitlement (-34018)` belongs here.
- `FAIL_DP_KEYCHAIN_NO_PROFILE_CAPABILITY` with
  `failure_class=INVALID_TEST_RUN`: crash, signal, absent/malformed result,
  external interruption, receipt-channel failure, or other evidence loss. It
  proves the run failed but leaves capability unproven.
- Any nonzero or unprovable cleanup sets
  `BLOCKED_KEYCHAIN_RESIDUE_UNPROVEN` regardless of the row result.

The top-level PASS/FAIL remains compatible with the accepted binary receipt
contract. `failure_class` prevents a run-control failure from being
misrepresented as a platform capability result.

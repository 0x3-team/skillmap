## Decision 1 — Additive P-256 proof suite

### Why P-256

The accepted M1.08 contract requires a non-exportable Ed25519 signing key. Apple documents Secure Enclave private signing for NIST P-256, while the current project evidence does not establish a supported non-exportable Ed25519 signing operation. Exportable Node/Web Crypto Ed25519, generic-password storage of Curve25519 bytes, key wrapping, WebAuthn, and software fallback do not satisfy the accepted custody boundary.

The project therefore selects an additive macOS-only P-256 suite. It does not alter the meaning of the accepted Ed25519 V1 bytes, fields, or vectors.

### Suite registry and downgrade defense

The new exact suite literal is:

```text
skillmap.ecdsa-p256-sha256.v2
```

The accepted V1 contract remains `skillmap.ed25519.v1` for registry/history purposes. M3 macOS advertises and accepts only the P-256 suite until a separately supported platform proves V1 custody.

Add this non-secret closed capability operation:

```http
GET /api/device-auth/v1/capabilities
Cache-Control: no-store
```

```json
{"api_version":"device-auth-v1","proof_suites":["skillmap.ecdsa-p256-sha256.v2"]}
```

The macOS client hard-pins that exact suite. It does not select the first server value, negotiate downward, omit the suite, retry with V1, or create a software key. Unreachable maps to transient/unreachable, not incompatible. Once initiation begins, the suite is immutable across the pairing, key binding, token family, access token, refresh generations, proof nonces, rotations, and idempotency receipts.

Every V2 proof-bearing request requires `X-SkillMap-Device-Proof-Suite: skillmap.ecdsa-p256-sha256.v2`. Initiation also carries `proof_suite` in its closed JSON body. Later operations compare the header to the immutable server record; they do not infer a suite from byte length or a thumbprint.

Reject before state lookup:

- missing or unknown suite;
- P-256 material labeled Ed25519, or Ed25519 material labeled P-256;
- V2 signature over a V1 preimage, or the reverse;
- suite header/body/record mismatch;
- a suite change during poll, exchange, refresh, protected access, or rotation;
- cross-suite rotation; it requires revoke and fresh pairing; and
- any client fallback after an incompatible-capabilities result.

### Public-key encoding and thumbprint

The P-256 public key wire value is canonical DER SubjectPublicKeyInfo:

- fixed prefix `3059301306072a8648ce3d020106082a8648ce3d030107034200`;
- followed by exactly 65 bytes `04 || X || Y`, where X and Y are 32-byte big-endian coordinates;
- exactly 91 total bytes;
- base64url without padding, exactly 122 ASCII characters; and
- thumbprint `sha256:<64 lowercase hex>` over those exact 91 SPKI bytes.

Reject compressed points, raw 65-byte wire values, alternate DER encodings or lengths, explicit curve parameters, trailing bytes, wrong OIDs, infinity, and points not on P-256. Store the suite beside every key and thumbprint.

### Signature encoding

The helper signs the complete proof message with Secure Enclave `SecKeyCreateSignature` using `.ecdsaSignatureMessageX962SHA256`. Apple returns X9.62 DER. The helper parses that DER with strict minimal-positive-integer rules and returns only fixed-width IEEE P1363 `r || s`:

- exactly 32-byte big-endian `r` followed by 32-byte big-endian `s`;
- exactly 64 total bytes;
- base64url without padding, exactly 86 ASCII characters; and
- `r` and `s` must each be in `[1, n-1]` for the P-256 order.

DER signatures are forbidden on the wire. M3 does **not** require low-S normalization: replay authority is the atomic device/purpose nonce rather than signature bytes, and imposing an undocumented platform-output constraint would create an avoidable compatibility failure. Both valid S ranges must verify; duplicate nonce use still fails.

### Native helper boundary

The signed/notarized native boundary has two deliberately separate stores and operation registries:

- Secure Enclave proof-key operations: `capabilities`, `create`, `publicKey`, `thumbprint`, `signProof`, `exists`, and `delete`; and
- Data Protection Keychain credential operations: `credential_load`, `credential_commit_exchange`, `credential_mark_refresh_pending`, `credential_commit_refresh`, and `credential_delete`.

The Secure Enclave item is `kSecClassKey` with `.privateKeyUsage`; the credential item is `kSecClassGenericPassword` and never receives `.privateKeyUsage`. No operation can convert, export, copy, or substitute one store into the other. Access tokens remain memory-only and never enter the helper or Keychain.

#### Signed caller and process boundary

The supported macOS cloud-auth entry is a signed `SkillMapLauncher`, not direct `node dist/cli.js`. The launcher verifies the retained JS/package/native hashes, creates a private non-inheritable broker pipe for the exact child it spawned, and directly spawns the helper. The helper obtains its parent audit/process identity and uses Security.framework code APIs to require the frozen launcher designated requirement, Team ID, bundle identifier, architecture, and accepted cdhash. It also self-verifies its own designated requirement, cdhash, entitlements, fixed package-relative path, and version before any Keychain read or secret-bearing output. A helper invoked directly by another local process fails before Keychain access.

Direct Node execution remains valid for local-only commands but cloud-auth commands fail with exit 4 when the authenticated launcher/broker is absent. This closes the signed-helper-as-credential-oracle problem; a hash check performed only by untrusted JavaScript is not sufficient.

All helper requests and responses use private pipes with a 4-byte unsigned big-endian length followed by a versioned canonical binary TLV payload. Frames are at most 8 KiB; unknown, repeated, out-of-order, missing, or oversized fields fail. Secret values never appear in argv, environment, inherited terminal stdout/stderr, JSON logs, crash descriptions, evidence, or support output. Stderr contains only fixed error codes. The launcher and CLI read the bounded stdout pipe directly into private memory and zero temporary mutable buffers after use.

#### Credential item and record

The exact Keychain query uses:

- `kSecUseDataProtectionKeychain = true`;
- `kSecClassGenericPassword`;
- `kSecAttrService = dev.skillmap.connector.device-auth.v1`;
- `kSecAttrAccount = sha256:<origin bytes>:<22-character device_id>`;
- the exact provisioned access group `TEAMID.dev.skillmap.connector.credentials` with no wildcard/shared fallback;
- `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`;
- `kSecAttrSynchronizable = false`; and
- one item per configured origin/device binding, maximum `kSecValueData` size 4 KiB.

The signing/notarization receipt must replace `TEAMID` with the actual team and prove the entitlements/access group on both launcher and helper. No user-presence flag is added because automatic refresh must work in an unlocked login session; a locked Keychain returns a fixed `secure_storage_unavailable` result without UI or downgrade.

Credential record V1 is a strict canonical binary record with magic `SKCR`, schema version `1`, total length, and these fields in numeric-ID order: configured-origin SHA-256, proof suite, Secure Enclave application-tag digest, `device_id`, `device_public_id`, `account_public_id`, `token_family_id`, generation, immutable family absolute expiry, current refresh token, and optional pending-refresh tuple. The pending tuple is exactly idempotency key, request digest, wire/response version, expected generation, and request-started-at. Public IDs retain their contract bounds; the refresh token is exactly 43 ASCII bytes; integer fields are unsigned 64-bit big-endian. Unknown/duplicate fields, invalid grammar, a binding mismatch, or a record over 4 KiB fails closed before returning a token.

#### Atomic operations and crash semantics

Credential operations acquire a symlink-safe, owner-only advisory lock in the global SkillMap application-support directory before `SecItemCopyMatching` plus mutation. The empty lock file is mode `0600`, contains no secret, is outside every workspace, and is opened with ownership/type checks. `SecItemAdd`, `SecItemUpdate` of the complete `kSecValueData`, and `SecItemDelete` are the only mutations.

- `credential_load` returns the validated record through the private broker pipe; it never prints to the inherited terminal.
- `credential_commit_exchange` requires absence, writes the complete generation-1 record once, and on an ambiguous result reloads and accepts only exact binding/token equality; any mismatch fails and triggers remote family revocation.
- `credential_mark_refresh_pending` requires the exact current family/generation and atomically replaces the record with the same refresh token plus pending tuple before the request is sent.
- `credential_commit_refresh` requires an exact pending tuple and exact response binding, then atomically replaces generation N/token N with generation N+1/token N+1 and clears pending. Crash before `SecItemUpdate` leaves N+pending; crash after it leaves only N+1 without pending.
- `credential_delete` is exact-query and idempotent; it verifies absence before reporting local deletion complete.

Concurrent helpers serialize on the lock. No operation writes a second refresh-token item, plaintext recovery file, preference, database, shell value, or workspace state. The M3.01 helper-boundary amendment, signed launcher, Keychain entitlements/accessibility behavior, locked/headless tests, and five credential operations require independent reacceptance before any cloud-auth implementation or support claim. Missing identity, signature, entitlement, broker, lock safety, Keychain access, or atomicity evidence keeps M3.03+ stopped.

## Decision 2 — Exact refresh response replay

### Selected mechanism

Use short-lived AEAD-sealed exact-response replay. Reject deterministic token reproduction.

Deterministic reproduction would couple credential security to a long-lived derivation root, expose every derivable token when that root and database receipts are compromised, conflict with M1.08's independently random token language, and still require a permanently stable serializer. AEAD preserves independently random tokens, detects database tampering, stores the exact original body rather than reconstructing it, and limits recoverable ciphertext to a short window.

Only refresh success is eligible. Exchange response loss remains governed by accepted M1.08: revoke/expire the orphan family and perform a fresh browser-confirmed pairing. Pairing codes, exchange codes, arbitrary bearer responses, and error bodies are not sealed.

### Token and byte semantics

On the first refresh attempt, the web service:

1. samples one pre-commit integer `response_issued_at` from the server clock and never changes it on retry;
2. requires `response_issued_at` to fit M1.08's unsigned Unix-seconds grammar and calculates `replay_until = response_issued_at + 600` and `runtime_purge_after = response_issued_at + 900` with checked arithmetic;
3. generates access and refresh tokens independently with a CSPRNG as 32 random bytes each;
4. base64url-encodes each without padding to exactly 43 characters and computes purpose-separated HMAC-SHA-256 lookup digests; raw tokens never enter Postgres;
5. anchors the new access expiry at `response_issued_at + 600`, the new refresh idle expiry at `response_issued_at + 2592000`, and the response's refresh-absolute remaining lifetime at the immutable family absolute expiry minus `response_issued_at`; replay time never extends any of them;
6. constructs the exact amended refresh success JSON once with `encodeRefreshSuccessV1` in fixed member order, compact UTF-8, no whitespace, and no locale-dependent conversion;
7. fixes `X-SkillMap-Response-Issued-At` to that same `response_issued_at`, encrypts the exact body bytes with AAD containing it, and submits the candidate transition; and
8. returns the same body buffer and fixed header values only after the DB reports `committed`.

The RPC independently samples/stores `db_committed_at` from `statement_timestamp()` and aborts the transaction unless `abs(db_committed_at - response_issued_at) <= 30 seconds`. `db_committed_at` is audit metadata only: it is not in the response, AAD, replay deadline, or credential-expiry calculation. This removes the impossible requirement to know commit time before encryption.

An exact retry decrypts and returns those same bytes. The byte-authoritative response is:

- HTTP status `200`;
- exact `Content-Type`, `Cache-Control`, `Referrer-Policy`, and `X-SkillMap-Response-Issued-At` values; and
- exact body bytes.

HTTP/2 framing and header order are not byte-authoritative. The first response and every replay must have identical status, the four fixed header values, `X-SkillMap-Response-Issued-At`, and body bytes. The client computes every relative access/refresh expiry from the original `response_issued_at`, never response-arrival or replay time. The family absolute expiry remains the immutable exchange-time bound; the amendment must redefine `refresh_absolute_expires_in` as its remaining duration at `response_issued_at`, never a reset to 90 days. If less than 60 access seconds remain, the client completes the local write and immediately performs a new serialized refresh.

### AEAD format

Use AES-256-GCM through Web Crypto:

- 32-byte key;
- fresh 12-byte CSPRNG nonce;
- 16-byte authentication tag appended to ciphertext;
- maximum ciphertext-plus-tag length 2 KiB;
- unique DB constraint on `(replay_key_version, nonce)`; and
- stored SHA-256 and plaintext byte length checked after decryption.

The exact AAD bytes are these lines plus a final newline:

```text
SKILLMAP-REFRESH-REPLAY-AAD-V1
skillmap.connector.v1
<proof suite>
<device_public_id>
<token_family_id>
<idempotency-key HMAC digest>
<request digest>
<prior generation>
<successor generation>
<response_issued_at Unix seconds>
<replay_until Unix seconds>
<response format version>
<response body sha256>
<response body byte length>
```

Any AAD field, key version, nonce, ciphertext/tag, length, or body-digest mismatch returns no credential, emits only a redacted security event, disables that family from further refresh until adjudicated, and never tries another key or serializer.

### TTL and cleanup

- Logical replay is allowed only while `server_now < response_issued_at + 600 seconds` and before access/family authority permits it.
- The primary runtime ciphertext row must be deleted no later than `response_issued_at + 900 seconds`; managed database backups may retain old ciphertext longer and are handled by replay-key destruction below.
- A non-secret immutable tombstone containing key/digest/generation/timing/result metadata remains through the token family's 90-day absolute lifetime.
- An exact retry at or after the logical deadline is retired-generation reuse: atomically revoke the family and return the accepted fixed `invalid_grant` response.
- Same idempotency key with a changed request digest is always `idempotency_conflict`, even after ciphertext cleanup, with no successor token.

The 600-second window matches M1.08's access/proof window and gives a crashed client one bounded restart opportunity. The primary row's 900-second deletion is **not** by itself a 15-minute exposure guarantee because managed backups and deleted secret versions may persist. The true cryptographic exposure bound is governed by the accepted epoch-key destruction contract below.

### Crash, retry, and concurrency rules

The signed native credential boundary maintains the one Keychain record defined above. `credential_mark_refresh_pending` persists the pending tuple before network transmission; `credential_commit_refresh` conditionally replaces it after response validation. It does not create a second refresh-token copy.

Before sending refresh N, it atomically persists the pending metadata. Every network retry reuses the same body and idempotency key but uses a fresh proof nonce. After a valid response, it atomically replaces N with N+1 and clears pending metadata. Access tokens remain memory-only.

The server generates a candidate N+1 response and calls one DB transition. In canonical lock order the RPC:

1. resolves exactly one presented refresh HMAC from a bounded, sorted active-key candidate set;
2. locks the family row;
3. checks an existing idempotency tombstone before treating N as malicious retired reuse;
4. locks the presented generation and receipt;
5. rechecks device, suite, key thumbprint, audience, scopes, revision, expiry and revocation;
6. consumes the fresh proof nonce;
7. verifies the 30-second `response_issued_at`/`db_committed_at` bound, inserts successor access/refresh digests with expiries derived from `response_issued_at`, retires N, advances the family, and inserts the tombstone and ciphertext row; and
8. commits once.

Outcomes are closed: `committed`, `exact_replay`, `idempotency_conflict`, `family_revoked`, or `unavailable`. A concurrent exact retry has one winner; the loser discards its candidate plaintext and decrypts the committed ciphertext. A second key/digest using retired N revokes the family. Revocation and expiry dominate replay. Crash before commit changes nothing. Commit followed by response loss replays exact bytes. There is never a replay grace that permits both refresh generations.

### Key custody and rotation

Use two long-lived versioned rings and one short-lived random epoch-key set:

1. `DEVICE_AUTH_LOOKUP_KEY_RING`: versioned 32-byte roots; derive purpose-separated HMAC keys with HKDF-SHA-256 labels for device code, user code, exchange code, idempotency key, access token and refresh token;
2. `DEVICE_AUTH_REPLAY_AEAD_EPOCH_KEYS`: independent random 32-byte AES-GCM keys, one per five-minute Unix epoch, never derived from a retained root; and
3. `DEVICE_AUTH_EDGE_IP_KEY_RING`: independent roots used only in the custom edge worker.

The lookup and IP rings are validated server-only secret objects with `primary` and a bounded map of numeric versions. Replay keys are separate provider/escrow objects keyed by `epoch_id = floor(response_issued_at / 300)`. None is ever a `NEXT_PUBLIC_*` value, Wrangler plaintext `vars`, repository file, DB value, log field, error detail, evidence payload, or browser value. Parse errors are redacted and fail closed.

The lookup ring retains an old version until no live artifact row references it. A replay epoch key may encrypt only responses whose `response_issued_at` is inside its five-minute epoch. The runtime and independent recovery escrow must both irreversibly destroy it no later than `epoch_end + 900 seconds + 30 seconds clock skew`; thus the maximum accepted key lifetime/exposure from epoch start is 1,230 seconds. Destruction evidence must include provider version state, runtime cache eviction, escrow deletion, an audit receipt, and a failed post-destruction retrieval/decrypt canary. No retained master/derivation seed may reconstruct a destroyed epoch key. The IP ring uses the primary/previous overlap below.

If the chosen runtime secret provider or escrow retains deleted versions, backups, snapshots, soft-delete recovery, or derivation material beyond 1,230 seconds, provider/escrow selection is a blocking gate. Pending a separately accepted amendment, the **true exposure bound** is the longest retention of any runtime, escrow, secret-backup, or managed-backup decryption key—not 900 or 1,230 seconds. The plan must report that longer bound rather than claiming short-lived recoverability.

### Disaster recovery

The recoverable source of truth is an approved external secret escrow plus the DB backup; a write-only provider value is not sufficient recovery evidence.

Before refresh traffic is enabled after restore:

- restore the database, then immediately purge every replay row whose `runtime_purge_after` has passed while preserving tombstones, including rows reintroduced from a managed backup;
- restore only epoch keys that remain inside their accepted 1,230-second lifetime; never restore or reconstruct a destroyed/expired epoch key merely because a backup contains ciphertext;
- prove one in-flight receipt decrypts to the recorded bytes; and
- if an unexpired receipt's AEAD key is irrecoverably missing, atomically revoke only the affected family, delete its ciphertext, record a redacted incident receipt, and require re-pairing.

Never regenerate a lost token, substitute another key, retain expired replay keys for old backups, or enable partial refresh traffic before the DB/runtime/escrow epoch inventory reconciles. Managed backups are assumed to retain ciphertext for their configured retention; security depends on verified epoch-key destruction. M3.14 must rehearse runtime/escrow destruction, backup restore after destruction, restore with a valid in-window key, and restore with a deliberately missing disposable key.

### Threat model

| Threat | Required property |
|---|---|
| DB read/backup compromise without server secrets | No bearer token recovery; ciphertext and HMACs only |
| Replay-key compromise without DB | No receipt/token recovery |
| DB or managed backup plus replay-key compromise | Exposure lasts for the actual key-retention overlap; accepted target is at most 1,230 seconds, but any provider/escrow deleted-version retention becomes the truthful longer bound and blocks acceptance |
| Lookup-key compromise | Live token lookups may be attacked; rotate and revoke affected version; no plaintext exists in DB |
| Malicious/tampered DB row | GCM/AAD/body-digest failure, no credential response |
| Decryption-oracle abuse | No public decrypt API; only exact-receipt path after proof/idempotency/family checks |
| Log/error/crash leakage | Fixed errors and redacted structured fields; canary scan includes ciphertext and token fixtures |
| Serializer drift | Stored bytes are replayed; response format version and golden hash gate changes |

## Decision 3 — Database role, RPC and privilege boundary

### Selected invocation model

Continue exposing only schema `api`. Do not expose `private`, `device_adapter`, or a new DeviceAuth schema. Do not introduce a direct database connection, login role, or custom request-role JWT in this milestone.

The online Next/OpenNext service uses the existing server-only Supabase `service_role` credential only through a new hard-allowlisted DeviceAuth RPC client. The SQL functions are owned by a new dedicated role:

```text
skillmap_device_auth_definer
NOLOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOREPLICATION NOBYPASSRLS
search_path = ''
```

No `anon`, `authenticated`, or `service_role` principal is a member of that role. All DeviceAuth tables enable and force RLS. Only the definer role receives the minimum table privileges and a role-targeted policy needed by its fixed SECURITY DEFINER functions. Request roles receive no table/view/sequence privileges.

Every `api.device_auth_*` function has an empty search path, fully qualified names, no dynamic SQL, exact parameter types/bounds, closed outcome, and a defense-in-depth signed-JWT claim check. Exact PostgreSQL `EXECUTE` grants are the primary invocation authority. Server RPCs additionally require `coalesce((select auth.jwt()) ->> 'role', '') = 'service_role'`. Every browser-owner RPC admits a caller only when all three predicates are true before any owner-state read or mutation:

```sql
coalesce((select auth.jwt()) ->> 'role', '') = 'authenticated'
and (select auth.uid()) is not null
and coalesce((select auth.jwt()) -> 'is_anonymous', 'true'::jsonb) = 'false'::jsonb
```

Only the type-preserved JSON boolean `false` equals `'false'::jsonb` and passes. JSON string `"false"` is distinct and denied. A missing or JSON-null claim is denied, as are string, number, object, array, or any other malformed/unexpected JSONB values, without a cast error. Ownership is then derived only from `auth.uid()`. The functions do not use deprecated `auth.role()`, caller-settable GUCs, `user_metadata`, or caller-supplied account IDs as authority.

Anonymous sign-ins are a frozen disabled provider invariant, not the sole authorization control. Candidate `supabase/config.toml` must retain `[auth].enable_anonymous_sign_ins = false`, and the generated local Auth container must expose effective `GOTRUE_EXTERNAL_ANONYMOUS_USERS_ENABLED=false`. The authorized hosted-project read-only Management API receipt must show `GET /v1/projects/{ref}/config/auth` field `EXTERNAL_ANONYMOUS_USERS_ENABLED=false`; a dashboard screenshot alone is supporting evidence, not the machine-readable authority. Local functional tests must show an anonymous sign-in attempt is denied with no new `auth.users.is_anonymous` row. Hosted production validation remains read-only: it binds the management-config response, function definitions, exact grants, and a rollback-only SQL claim fixture; it must not toggle anonymous sign-ins or create a test user. Missing access or disagreement between static, effective-local, and hosted values blocks acceptance.

This design limits service-role use at the object and application layers without falsely claiming that `service_role` itself does not bypass RLS. Acceptance requires proving all revokes/grants on the real target; the plan does not infer them from local SQL text.

#### Fixed transaction-level lock protocol

The single frozen lock identity is the two-int32 advisory-lock pair `(1397442892, 1145132372)`, whose labels are hexadecimal `0x534B494C` (`SKIL`) and `0x44415554` (`DAUT`). It is a dedicated SkillMap DeviceAuth cutover namespace and must not be reused by account, import, route, deletion, or rate-limit locking.

Migration `20260810050000_skillmap_device_auth_legacy_admission_fence.sql` replaces all six superseded functions above without changing their signatures, result shapes, enabled-path behavior, owners, or existing EXECUTE grants. The migration first asserts their clean-reset and target owners are exactly `postgres`, `prosecdef` is true, and `proconfig` fixes an empty search path; any mismatch aborts rather than inferring authority. Each replacement has no declaration initializer that reads state, calls `auth.*`, or samples time. Its first two executable operations are, in this order:

```sql
perform pg_catalog.pg_advisory_xact_lock_shared(1397442892, 1145132372);
perform private.device_auth_assert_legacy_authority_enabled();
```

Only after both return may the function read identity, time, device/token state, or mutate anything. The three authenticated owner entrypoints then apply the same permanent-user predicate as the four new owner RPCs—exact role `authenticated`, non-null `auth.uid()`, and `coalesce((select auth.jwt()) -> 'is_anonymous', 'true'::jsonb) = 'false'::jsonb`—before their existing ownership logic. The three service adapters retain the exact service-role boundary. Because the lock is transaction-level, every admitted legacy operation holds the shared lock through commit or rollback; a helper call cannot release it early.

#### DB-owned authority flag and privileges

The fifth migration creates exactly one row in `private.device_auth_authority_control`:

```text
control_key text primary key = 'legacy_device_authority'
legacy_device_authority_enabled boolean not null = true
revision bigint not null = 1, revision > 0
changed_at timestamptz not null = statement_timestamp()
```

The table is owned by `skillmap_device_auth_definer`, has RLS enabled and forced, and has one role-targeted SELECT policy plus one UPDATE policy for that owner and singleton key. All table privileges are revoked from PUBLIC, `anon`, `authenticated`, `service_role`, `skillmap_vault_definer`, and every other application role; it has no API view, RPC, publication, sequence, or direct client grant. `private.device_auth_assert_legacy_authority_enabled()` is SECURITY DEFINER, owned by `skillmap_device_auth_definer`, has `search_path=''`, returns no flag value, and raises fixed SQLSTATE `42501` unless the singleton exists and is exactly true. EXECUTE is revoked from PUBLIC and all request/application roles and granted only to the asserted `postgres` owner of the six fenced functions.

A BEFORE UPDATE/DELETE trigger owned by the definer role permits only the single forward transition `true/revision R -> false/revision R+1` with a fresh `changed_at`; delete, key change, revision skip, false-to-true, and any second transition fail. Thus a committed disable is irreversible by ordinary SQL/migrations; a failed cutover transaction rolls the transition back to true with everything else.

#### Sixth and final atomic cutover

Before `20260810060000_skillmap_device_auth_atomic_cutover.sql`, an external gate binds the fifth-migration hash and tests, accepted replacement RPC/pgTAP hashes, predecessor import regressions, signed launcher/helper receipt, both M1.08 amendments, the replacement-aware artifact ID, and zero unsafe legacy rows/nonterminal operations/unmigrated references. The deployed artifact can serve existing workflows through either authority generation but keeps new Connector DeviceAuth disabled; legacy authority is not disabled early.

Inside one transaction, the sixth migration:

1. asserts the exact migration principal, control row/version, fenced function definitions/owners/grants, replacement definitions, and accepted artifact/evidence identifiers;
2. obtains the matching exclusive `pg_catalog.pg_advisory_xact_lock(1397442892, 1145132372)`, which cannot succeed until every admitted shared-lock legacy transaction has ended;
3. flips the singleton from true/R to false/R+1 and proves the current transaction is the only granted holder for that advisory-lock identity;
4. under that fence, rechecks zero live legacy tokens, nonterminal legacy operations, unmigrated references, and other unsafe state using exact locked-table predicates;
5. grants only the frozen replacement RPC EXECUTE matrix, revokes only the six exact legacy grants above, and leaves the four import adapters unchanged;
6. reloads the PostgREST schema cache and commits once.

The linearization rule is lock acquisition, not request arrival. A legacy call that acquires the shared lock before the cutover's exclusive lock may finish; the cutover waits and then rechecks its result. A call already queued, or arriving while the exclusive lock is held, cannot pass the flag check: after a successful cutover it either fails the now-revoked EXECUTE check or acquires shared after commit and receives `42501` from the false flag before state access. If any cutover assertion, grant, revoke, or cache action fails, the transaction rolls back the flag and privilege changes together; queued legacy calls then acquire shared, see true, and retain the previous behavior. There is no partial flip, admitted call running across the cutover commit, or no-authority interval.

If unsafe live state exists, stop: old token material cannot be inferred into proof-suite/key/family authority. Use a separately accepted safe migration/revoke-and-re-pair procedure, then rerun the sixth cutover. Never backfill a proof suite or perform a best-effort partial revoke.

Replace the existing immutable-display trigger forward so only the new definer-owned rename RPC can change `display_name`, with `revision = old.revision + 1`. No caller supplies the new revision. Other stable identity, account, platform, connector, issued-at, and public-ID fields remain immutable. The accepted M2.11 test/evidence bytes remain immutable; implementation adds an append-only supersession receipt naming the fenced definitions, intentionally changed grants, and old/new test hashes.

## Decision 4 — Strict raw JSON

Pin `jsonc-parser@3.3.1` in `apps/web` after lockfile/audit review. It has no dependencies and provides decoded property callbacks and exact offsets. It is selected over `JSON.parse`, a hand-written scanner, or normalizing middleware. The fact that it supports JSON-with-comments and fault-tolerant parsing is not relied on: DeviceAuth configures strict JSON and rejects every reported error.

`apps/web/lib/device-auth/raw-json.server.ts` owns `readStrictDeviceAuthJson`, `scanStrictJson`, and `StrictDeviceAuthJsonError` with this order:

1. require the exact allowed JSON content type and forbid content encoding/query where the operation contract forbids it;
2. read the request stream once with an operation-specific byte ceiling; reject a declared or observed overflow before allocation grows past the ceiling;
3. reject UTF-8 BOM bytes and NUL, then decode with `TextDecoder('utf-8', { fatal: true })`;
4. call `visit`/`parseTree` with `disallowComments: true`, `allowTrailingComma: false`, and `allowEmptyContent: false`;
5. reject any parser error, trailing value/data, non-object root, excessive depth/member count, or numeric token outside the schema-safe profile;
6. maintain one `Set` per object and reject duplicate **decoded** property names recursively, including `"a"` versus `"\u0061"`;
7. only after the scan passes, materialize the value, traverse every key/string for NFC and control-character rules, and apply the exact generated route schema; and
8. retain the original bytes unchanged for the body SHA-256 and proof/idempotency preimages.

Parsing and structural validation occur before public-key lookup, proof verification, rate identity lookup, Supabase calls, or operation-specific state reads. Parser errors collapse to the fixed M1.08 `invalid_request` body and do not echo input.

Required adversarial fixtures include root/nested/escape-equivalent duplicates, duplicate `__proto__`/`constructor`, BOM, NUL, malformed/overlong UTF-8, unescaped controls, comments, trailing comma/data, empty input, scalar/array root, excessive depth/members/string/body, `-0`, exponent/unsafe integer cases, non-NFC strings, unknown fields, and property-order/whitespace variants that must produce different body hashes. The same fixtures must pass identically on Node 22/24, Next production, OpenNext build, and emitted Workerd. Any divergence blocks M3.03; there is no production fallback to `JSON.parse` or the local connector's body parser.

## Decision 5 — Distributed rate-limit authority

### Non-IP quotas

Device key, account, token family, pairing, grant, poll schedule, and browser-session attempt limits are authoritative Postgres rolling buckets. Each relevant bucket is locked and advanced in the same transaction as the protocol transition. N succeeds, N+1 returns fixed `rate_limited`, and a rejected request does not partially mutate protocol state.

### Source-IP quotas

The M1.08 source-IP limits for initiation and browser-code attempts are enforced in a dedicated SQLite Durable Object, not in `apps/web/lib/security/rate-limit-core.ts`, not in a per-isolate map, and not by Cloudflare's Rate Limiting binding. Cloudflare documents Rate Limiting binding counters as location-local and eventually consistent; they cannot prove the exact cross-location N/N+1 contract. Durable Objects provide a globally unique object identity and serialized transactional storage.

Exact ownership:

- `apps/web/cloudflare-worker.ts` — custom OpenNext entry; strips any client-supplied internal edge header, performs the pre-Next edge gate, strips raw `CF-Connecting-IP` before forwarding a DeviceAuth request, re-exports the OpenNext handler, and exports `DeviceAuthIpRateLimiter`;
- `apps/web/cloudflare/device-auth-ip-rate-limiter.ts` — `DeviceAuthIpRateLimiter` Durable Object with SQLite-backed rolling timestamp buckets;
- `apps/web/cloudflare/device-auth-edge-gate.ts` — IP normalization, HMAC object naming, primary/previous dual-write rotation, fixed failure mapping;
- `apps/web/cloudflare-env.d.ts` — exact binding/secret types; and
- new candidate `apps/web/wrangler.jsonc` — custom worker entry, `DEVICE_AUTH_IP_RATE_LIMITER` binding, and declarative SQLite Durable Object export. The candidate has no such file today. Dirty-main `apps/web/wrangler.jsonc` at SHA-256 `85985090d000cd17805e5f0b1fd0a2d677243c635ca2abd94d3402daab06c1b2` is reference-only input; do not copy it wholesale or place secret keys in `vars`.

The custom worker reads raw `CF-Connecting-IP` only at the edge. It derives a domain-separated HMAC object name and never sends the raw address to Next, Postgres, logs, analytics, receipts, support artifacts, or the Durable Object. The Durable Object stores only the pseudonymous bucket identity, operation class, and bounded rolling timestamps/counters; expired rows are deleted after the 10-minute window.

IP key rotation uses a primary and optional previous key, but there is no transaction across their two Durable Objects. During the overlap the edge gate derives both object IDs first, then calls **previous first and current second**, sequentially, for every attempt. Each call is one atomic `checkAndIncrement` inside that object and returns `allowed` plus its positive `retry_after` when denied. The edge gate never calls current before previous, never runs the calls in parallel, and never compensates or decrements a successful call.

The combined outcome is exact:

- allow only when every required object returns `allowed`;
- if both calls complete and either denies, return `rate_limited` with `retry_after = max(all denied retry_after values)`; an allow/increment in the other object remains as conservative overcount;
- if either call is unavailable, times out, returns malformed data, or has an indeterminate response, return `temporarily_unavailable` with `retry_after: 0`, stop before any not-yet-called object, and retain any earlier increment as conservative overcount;
- a response lost after an object commit is treated as indeterminate failure, never retried inside the same edge request and never rolled back; a later client retry may increment again and overcount but cannot bypass the quota; and
- if the previous object definitively denies but the current call then fails, failure wins and the response is `temporarily_unavailable`, because the full two-object state was not observed.

For at least one complete 10-minute rolling window plus the accepted clock-skew allowance after rotation, every request is dual-written in that fixed order. The previous key can be removed only after the current object has received a complete rolling window of dual writes and a cleanup/rotation receipt proves it. This prevents a rotation-boundary reset while explicitly accepting conservative overcount as the safe partial-failure bias. Raw IP and HMAC values are never emitted.

For the two targeted operations, missing binding, missing/invalid key ring, Durable Object timeout, storage error, or malformed Cloudflare source header fails closed as `temporarily_unavailable`; it does not fall back to per-isolate memory. Local tests inject a test-only adapter that cannot be selected by production configuration.

Acceptance requires Workerd N/N+1 tests and a later authorized two-location preview showing the combined quota, exact `retry_after`, no raw-IP persistence/logging, fail-closed behavior, config/export identity, and rollback kill switch. Until then the decision is frozen but not live-verified.

## Decision 7 — Lifecycle state machines

### Pairing

```text
pending -> approved -> grant_issued -> exchanged
pending -> denied | cancelled | expired
approved | grant_issued -> cancelled | expired
```

Terminal states are immutable. One browser approval, one grant, and one exchange can win. Exchange response loss never replays a secret response.

### General idempotency

```text
absent -> committed
same key + same digest -> committed response/receipt replay
same key + changed digest -> idempotency_conflict, no mutation
```

Do not persist an externally observable `in_progress` state across transaction boundaries. Crash before commit is absence; crash after commit is the committed receipt.

### Refresh family

```text
active(N) --one atomic commit--> active(N+1)
retired N + exact receipt inside 600s -> exact N+1 response
retired N + different request OR expired exact replay -> whole family revoked
active -> idle_expired | absolute_expired | revoked | compromised
```

Expiry/revocation is terminal. There is no dual-generation acceptance window.

### Device key

```text
active(K) -> rotation_pending(old+new proof) -> active(K+1, same suite)
active | rotation_pending -> revoked | compromised
```

The old key is not deleted locally until a signed status/rotation receipt proves the new binding. Ambiguity reconciles; it never guesses. Cross-suite change requires fresh pairing.

### Local credential

```text
signed_out -> pairing -> pending_exchange -> authenticated(N)
authenticated(N) --credential_mark_refresh_pending--> refresh_pending(N)
refresh_pending(N) --same idempotency/digest retry--> refresh_pending(N)
refresh_pending(N) --credential_commit_refresh--> authenticated(N+1)
authenticated -> remote_revoke_pending -> remote_terminal -> local_deleted
```

Crash recovery calls `credential_load` through the verified launcher/helper broker, reads one versioned Keychain record and pending tuple, and retries only that exact refresh. It never uses replay arrival time for expiry, resumes an old browser pairing, invokes the helper directly, or creates a plaintext fallback.

### Owner mutation and rate bucket

Owner rename/revoke is observed revision R, RPC with expected R, success at R+1, then reread. Conflict returns no optimistic authority. A rate bucket below N increments atomically with the operation; N+1 rejects and performs no protocol transition.

### Legacy authority admission

```text
enabled(R) + shared holder -> admitted legacy transaction -> commit|rollback -> enabled(R)
enabled(R) --exclusive cutover transaction--> disabled(R+1)
disabled(R+1) -> terminal; legacy call denied before state access
failed exclusive cutover -> transaction rollback -> enabled(R)
```

Arrival time does not establish admission. Only acquisition of the shared lock followed by a true flag does. The exclusive transition waits for every admitted holder, makes false terminal in the same transaction as the grant flip, and releases queued calls only after commit or rollback.

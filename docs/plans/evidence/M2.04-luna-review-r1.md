## Findings

### P2 — failed activation requests are not idempotent across state change

The M2.02 contract requires that the same idempotency key with the same input return the same outcome, while conflicting reuse fails closed. The implementation persists only successful activation receipts in `private.managed_skill_activation_receipts`. Missing, stale, foreign, malformed, and noneligible requests raise immediately and leave no durable command/rejection receipt.

Consequently, a request that is rejected as noneligible can be retried with the same key and identical arguments after a later lifecycle/eligibility change and can then activate successfully. A missing-resource request can likewise change from rejection to success if the resource is later created. That is a different outcome for byte-equivalent input and permits a rejected operation identity to be replayed under newer state. The focused test exercises successful replay and conflicting successful reuse, but does not exercise rejected-key replay after the target changes.

This violates M2.02 section 4.2 and M1.06 §9.2–§9.3. It is a P2 acceptance blocker because the function is the activation authority intended for later exposure and because replay is part of the frozen CAS contract. The fix must be a forward-compatible durable decision/rejection record or an equivalent design that consumes the operation identity and replays the original bounded denial without permitting a later success; it must preserve the exact public interface and error-privacy requirements. Do not repair by allowing last-writer-wins or by weakening the idempotency key scope.

### P3 — lifecycle timestamp invariants are weaker than their documented meaning

The release trigger makes `activated_at` server-owned on insertion/transition to `active`, and prevents changing it once non-null. It does not prevent a direct internal update from setting `activated_at` on a non-active release, nor does it prevent setting `revoked_at` on a non-active release after activation. A non-active release can therefore carry timestamp facts that do not correspond to the documented first-active/revocation events. The activation function separately rejects a revoked release, so this does not create an activation allow in the current ungranted phase, but the invariant should be tightened before lifecycle mutation is exposed.

### P3 — registry mapping is deferred but not yet represented at the function boundary

The activation functions raise ad hoc `P0001` exceptions with generic English messages. The functions are ungranted to `public`, `anon`, `authenticated`, and `service_role`, so this is not current public disclosure and does not independently block M2.04. M2.10 must map all activation failures through the M2.02 registry, preserve indistinguishable unavailable/conflict behavior, and perform the owner transfer, policy creation, and reviewed grants atomically before any exposure.

### P3 — focused coverage does not assert all newly created receipt-table isolation

The implementation enables and forces RLS on the durable activation-receipt table and revokes application privileges, but the focused privilege assertions primarily enumerate the version/release tables and API function. Add explicit receipt-table zero-policy, FORCE RLS, and role-privilege assertions in the owning future gate or a forward test repair. The current ungranted state and supplied catalog receipts make this a coverage gap, not a demonstrated exposure.

## Phase-local owner bridge adjudication

The documented bridge is safe as a bounded M2.04 dependency, not a P1/P2 by itself. FORCE RLS with zero policies intentionally makes the future non-BYPASSRLS `skillmap_vault_definer` unusable at this phase. The two activation functions are ungranted to every application role, and the temporary `postgres` ownership does not create application reachability. M2.10 must, in one atomic forward transaction, create the exact owner policies, transfer both function owners to `skillmap_vault_definer`, and add only reviewed grants; no grant may precede transfer. If M2.10 exposes either function before that transfer or leaves the temporary owner in place, it becomes a blocking security/convention defect.

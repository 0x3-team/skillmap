## Contract and implementation review

### Identity and composite ownership

The table has an internal UUID, checked globally unique `msf_` public ID, repeated account/skill/version UUIDs, file metadata, executable declaration, ordinal, and server-owned timestamp (migration:5-20). The account/skill FK and account/skill/version FK both use composite scope and cascade on delete (migration:26-33). Supporting identity keys include `(account_id,id)` and `(account_id,managed_skill_id,version_id,id)` (migration:22-25). The focused suite verifies the exact column shape, public-ID grammar, both composite FKs, and cascade actions (focused test:21-63,697-707).

The adversarial fixtures exercise cross-account, cross-skill, and cross-version attachment failures with noncolliding ordinals so the FK is the determining rejection (focused test:570-599). This prevents a single-column UUID attachment from bypassing account or Managed Skill scope.

### Path, media, digest, storage, ordinal, and byte constraints

The SQL path constraint enforces 1–512 UTF-8 bytes, NFC spelling, relative form, no leading slash, no drive/URI scheme prefix, no backslash, no empty segment, no dot segment, no control character, and at most 32 segments (migration:36-47). The test covers the SQL-representable M1.04 denials plus exact 512-byte/32-segment acceptance, 513-byte rejection, 33-segment rejection, and non-NFC rejection (focused test:367-411,442-492). M1.03 remains the authority for canonical cloud path spelling and its collision key, including rejection before trust of percent-encoded traversal and case-fold aliases (M1.03:105-115); M1.04 owns the pre-upload scanner and repeats those denial classes (M1.04:15-30,100-115). M2.05 correctly does not add URL decoding or a second scanner/parser; it stores already-canonical metadata at this phase boundary (acceptance:17, M2.02 evidence:176-184).

Media type is a nonempty NFC/control-free relational value trimmed at both ends and bounded to 128 UTF-8 bytes (migration:48-54). The opaque storage key is nonempty, control-free, and bounded to 512 UTF-8 bytes (migration:61-65). The focused suite checks 129-byte media and 513-byte storage rejection (focused test:520-528). These are defensible phase-local storage limits: M2.02 freezes bounded fields but no exact media/storage grammar (M2.02 evidence:176-180), while M2.06 owns the exact object key convention and binding (M2.02 evidence:186-194). No MIME allowlist or M2.06 key grammar is invented.

The file digest is exactly lowercase `sha256:` plus 64 lowercase hexadecimal characters; ordinal is nonnegative; path and ordinal are unique per account/version; storage keys are globally unique (migration:55-73). The focused suite verifies the digest grammar, negative ordinal, duplicate path/ordinal/storage key, and uppercase/malformed digest denials (focused test:115-149,505-558). This matches M1.03’s exact-file digest rule (M1.03:74-78) and M1.05’s immutable file-digest semantics (M1.05:28-37,137-150).

Declared file bytes are `bigint` in the inclusive range `0..16,777,216`, and `SKILL.md` is bounded to `1,048,576` bytes (migration:13-16,55-60). The focused suite accepts 16 MiB and 1 MiB exactly, rejects each plus one, and rejects negative bytes (focused test:525-568). The inherited count, per-file, aggregate, and `SKILL.md` values are the exact M1.03/M1.04 limits (M1.03:142-166; M1.04:51-65).

### Immutability and deletion semantics

The trigger rejects updates to every identity/content coordinate: internal and public IDs, account/skill/version ownership, path, media type, byte size, file digest, storage key, executable flag, ordinal, and creation timestamp (migration:92-125). Inserts always replace a caller timestamp with `statement_timestamp()` (migration:120-123). The focused test confirms representative path, digest, and account-coordinate update failures (focused test:596-617), while the trigger source enumerates the full immutable set. Deletes remain legal, as required for later child-to-parent cleanup; M1.05 requires all frozen fields to reject updates after visibility (M1.05:137-150), and the M2.05 acceptance explicitly preserves deletion for cleanup (acceptance:19-23).

### Deferred aggregate enforcement and race safety

`private.enforce_managed_version_file_bounds()` first locks the exact parent version row, returns harmlessly when a cascade has already removed that parent, then locks all matching child file rows in deterministic UUID order before counting and summing (migration:132-209). The constraint trigger is `AFTER INSERT OR UPDATE OR DELETE`, `DEFERRABLE`, and `INITIALLY DEFERRED` (migration:211-215). The aggregate uses `count()::bigint` and a numeric byte sum, then rejects more than 2,048 files or more than 67,108,864 bytes (migration:188-205). No external operation occurs while the relational locks are held (migration:173-175; focused test:242-262).

The focused suite accepts exactly 2,048 files and exactly 64 MiB, rejects 2,049 files at immediate deferred enforcement, accepts a second exact 64 MiB version, and rejects aggregate bytes plus one (focused test:633-691). It also verifies the deferred-trigger shape, parent-before-file ordering, ordered file locking, and both exact bounds from the function definition (focused test:227-262). The implementation follows M2.02’s global order of version then files and no external effect (M2.02 evidence:84-99,172-184).

There is no explicit two-session concurrent quota fixture in this 74-assertion suite. I classify that as **P3 nonblocking test-evidence residual**, not P2: the correctness-critical serialization is directly demonstrable from the parent-row `FOR UPDATE` followed by deterministic child-row locks and a fresh aggregate query, and the supplied parent receipts include clean reset, focused 74/74, and zero residue. A future concurrency fixture should still race same-version quota inserts and prove one committed aggregate cannot exceed either bound.

### Cascade safety

Both ownership FKs cascade to file rows (migration:26-33). The deferred trigger explicitly tolerates a missing parent during cascade cleanup (migration:167-171), and the test deletes the account fixture then verifies zero file rows, zero version rows, and zero Managed Skill rows (focused test:693-707). This preserves the required child-to-parent deletion order without orphan storage behavior; M2.02 confirms no storage object can be created by M2.05 (M2.02 evidence:180-182).

### RLS and ACL isolation

The table enables and forces RLS, creates zero policies, and explicitly revokes table and trigger-function privileges from `public`, `anon`, `authenticated`, `service_role`, and the future vault-definer role (migration:217-229). The focused suite verifies forced RLS, zero policies, application-role denial, function-execution denial, and no `PUBLIC` table privilege (focused test:175-207). No application behavior is exposed before later policy/grant phases, consistent with M2.02’s deny-by-default and M2.10–M2.12 grant boundary (M2.02:75-82,101-105). No new schema grant, API projection, security-definer function, or storage policy is introduced.

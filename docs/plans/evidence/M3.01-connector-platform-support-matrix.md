## Decision

M3.01 cannot promote macOS to `SUPPORTED_NOW`. M1.08 R11 freezes a non-exportable Ed25519 private signing key, while Apple’s documented Secure Enclave supports only 256-bit elliptic-curve private keys (the P-256 signing path), not Ed25519. Node can generate and export Ed25519 key material, but that is not OS-custodied non-exportable signing and is forbidden as a production fallback.

The recommended next action is an additive, independently reviewed M1.08 amendment for a macOS-only P-256 proof variant. The amendment must define the public-key encoding, signature encoding, thumbprint input, algorithm registry entry, and Node/OpenNext/Cloudflare verification vectors; it must not silently reinterpret the existing Ed25519 contract. Until that amendment is accepted, M3.03+ remains blocked.

Current official platform evidence:

- Apple, [Protecting keys with the Secure Enclave](https://developer.apple.com/documentation/security/protecting-keys-with-the-secure-enclave): Secure Enclave private signing keys are non-exportable, require hardware support, and work only with NIST P-256; keys must be generated in the Secure Enclave and cannot import pre-existing key material.
- Apple, [`kSecAttrTokenIDSecureEnclave`](https://developer.apple.com/documentation/security/ksecattrtokenidsecureenclave): only 256-bit elliptic-curve private keys are supported and they must be generated directly in the Secure Enclave.
- Apple, [`SecKeyCopyExternalRepresentation`](https://developer.apple.com/documentation/security/1643698-seckeycopyexternalrepresentation): export fails for keys bound to the Secure Enclave or marked non-extractable.
- Apple, [Keychains](https://developer.apple.com/documentation/security/keychains): macOS supports multiple keychains, typically managed by the user through Keychain Access, and exposes APIs to manipulate keychains directly. The page's automatic lock sentence is in its iOS overview, not macOS evidence.
- Apple, [`SecKeychainLock`](https://developer.apple.com/documentation/security/seckeychainlock%28_%3A%29): macOS can explicitly lock a keychain (passing `NULL` targets the default keychain; the API is deprecated). Whether the Secure Enclave item accessed by this helper fails closed in the locked state requires an explicit lock-state probe and is not claimed here.
- Apple, [`kSecAttrAccessibleWhenUnlockedThisDeviceOnly`](https://developer.apple.com/documentation/security/ksecattraccessiblewhenunlockedthisdeviceonly): Apple defines this attribute as accessible only while the device is unlocked; the candidate records the desired restriction but has no macOS runtime proof for this helper yet.
- Apple, [`errSecMissingEntitlement`](https://developer.apple.com/documentation/security/errsecmissingentitlement): missing keychain entitlements are a real failure mode for a native helper/application.
- Node, [Crypto](https://nodejs.org/api/crypto.html): `generateKeyPairSync('ed25519')` and `sign`/`verify` are supported; Node can export raw/PKCS#8/JWK key material, so Node crypto alone does not satisfy non-exportable custody.
- Node, [v22 Web Crypto](https://nodejs.org/download/release/v22.23.1/docs/api/webcrypto.html): Ed25519 is stable from v22.13.0 and supports import/export/sign/verify; the current supported runtime target is Node 22 and 24 LTS.
- Node, [release schedule](https://nodejs.org/en/about/previous-releases): Node 22 and 24 are LTS; Node 20 is EOL and is not carried into M3 support.
- OpenNext, [Cloudflare adapter](https://opennext.js.org/cloudflare): the adapter emits a Worker-compatible build using the Next.js Node runtime and Cloudflare’s Node-compatible runtime APIs; this is not a proof that this candidate’s future DeviceAuth handler has been emitted.
- OpenNext, [CLI/build/deploy](https://opennext.js.org/cloudflare/cli): build transforms the Next output and `preview` runs through Wrangler; deploy is a later M3.14 action, not performed here.
- Cloudflare, [Web Crypto](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/): Workers support ECDSA and Ed25519 verification through Web Crypto, with documented differences from Node; Ed25519 private-key raw import is not supported by the legacy `NODE-ED25519` path.
- Cloudflare, [Node.js Crypto/TLS compatibility](https://developers.cloudflare.com/changelog/post/2025-04-08-nodejs-crypto-and-tls/): `node:crypto` is available with `nodejs_compat`; the emitted Worker must still be tested with the selected algorithm and exact encoding.

## Custody and helper contract to carry into M3.02

1. The private key is generated by the native helper using Secure Enclave P-256, stored as a permanent keychain item with restrictive access control, and never exported. `SecKeyCreateSignature` is the only private-key operation exposed to the CLI.
2. Public key, thumbprint, and `exists` metadata may cross the helper boundary; private key bytes, refresh tokens, and access tokens may not. Access tokens remain memory-only; refresh binding remains keychain-only.
3. The helper must be a prebuilt, signed artifact selected by path, SHA-256, signature, and architecture before any secret operation. There is no install script, runtime download, consumer compilation, or `/usr/bin/security` secret argument.
4. Locked keychain, denied access, missing entitlement, missing helper, wrong architecture, invalid signature, corrupt item, partial write, and deletion failure are typed fail-closed outcomes. The locked-keychain behavior remains a probe requirement until verified. No memory/file fallback is selectable in production.
5. A headless/SSH invocation must not unlock the login keychain or display an authentication prompt. It returns a storage-locked/unsupported result and leaves remote credentials untouched; an explicit foreground user action is required.
6. Install/update/uninstall are passive lifecycle operations. Login is explicit; normal uninstall requires logout first, then hook removal, then package removal. Workspace, skills, quarantine, and owner data are outside connector cleanup.

## Bounded spike receipt

Command: `swiftc -framework Security scripts/m3-01-macos-secure-enclave-spike.swift -o <temporary> && <temporary>`

The spike requested `kSecAttrTokenIDSecureEnclave`, 256-bit `kSecAttrKeyTypeECSECPrimeRandom`, `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` plus `SecAccessControlCreateFlags.privateKeyUsage`, generated one disposable key, attempted a signature, attempted external representation, and scheduled deletion. It did not perform a lock/unlock probe. On this unsigned Swift CLI process it stopped at key generation with `OSStatus -34018` (`errSecMissingEntitlement`); no key material was printed and no persistent item remained. This is useful failure evidence, not a successful custody or lock-state proof: a signed/entitled helper and explicit lock-state probe are still required.

Node compatibility checks passed locally on v22.23.1:

- Node `crypto` Ed25519 sign/verify: pass; PKCS#8 export was possible, therefore this is not custody evidence.
- Node Web Crypto Ed25519 sign/verify: pass.
- Node Web Crypto ECDSA P-256 sign/verify: pass.

Cloudflare/OpenNext compatibility is documented but not emitted-artifact verified in this slice. M3.02 must add exact positive/negative proof vectors and run them against the generated OpenNext Worker/Wrangler artifact, including the chosen P-256 signature encoding if the amendment is accepted.

## Stop conditions and next action

- **Blocking decision:** M1.08 Ed25519 plus non-exportability has no supported Apple Secure Enclave implementation in the current official evidence.
- **Lock-state evidence gap:** macOS keychain lock behavior for this Secure Enclave helper requires an explicit signed-helper probe; do not infer it from the iOS overview or promote the candidate while it is absent.
- **Recommended resolution:** independently review and accept an additive P-256 M1.08 variant limited to the tested macOS/helper matrix, or provide a signed native proof of non-exportable Ed25519 custody.
- **Separate M3.02 blocker:** freeze a response-loss replay mechanism; the dirty `20260727061900` migration metadata cannot reproduce secret refresh output.
- **R0 lineage:** use `R0-M3.01-candidate-reconciliation.json`; do not adopt dirty-main migrations or source wholesale.

## Binary decision

One more local slice is worthwhile, but only as an additive, non-product,
read-only readiness inspector with fully synthetic tests. It can remove avoidable
surprises before an authorized Apple signing run: missing or ambiguous Developer
ID Application identities, wrong Team/App ID/profile relationships, unsafe
login-keychain dependence, missing command-line tools, and accidental metadata or
private-key leakage.

This slice **cannot** satisfy M3.01 custody acceptance, promote macOS to
`SUPPORTED_NOW`, sign or notarize a launcher/helper, prove Secure Enclave key
generation or non-exportability, prove locked/headless behavior, verify Apple
online revocation/notary state, or make product M3.03 eligible. Its strongest
positive result is exactly `READY_FOR_AUTHORIZED_SIGNING_PROOF`: the local
preconditions appear suitable for a separately authorized, mutable signing and
runtime proof. It is not a release or custody verdict.

## Pre-provisioned task root and canonical-path contract

The **task root** and the CLI **scratch root** are different objects:

- The task root is provisioned later by the authorized operator, before
  inventory mode starts. Its exact lexical form is
  `<verified-disposable-home>/.skillmap-m3-apple-readiness/<run-id>`, where
  `<run-id>` matches `^[a-z0-9][a-z0-9-]{0,47}$`. Both
  `.skillmap-m3-apple-readiness` and `<run-id>` already exist, are directories,
  are owned by `disposable_uid`, have mode exactly 0700, have link count 1, and
  have no ACL entries. The inspector does not provision them.
- The scratch root is a fresh
  `<os.tmpdir()>/skillmap-m303-apple-readiness-<random>` created by the CLI for
  its own synthetic adapter/capture lifecycle only. It may never be the task
  root or an ancestor/descendant of it, and no request, keychain, or profile may
  resolve inside it. Cleanup removes only this captured scratch path. It never
  removes the operator-owned task root.

The only accepted task-root layout is:

```text
<task-root>/request.json
<task-root>/signing.keychain-db
<task-root>/profiles/launcher.provisionprofile
<task-root>/profiles/helper.provisionprofile
<task-root>/profiles/alternates/<ascii-name>.provisionprofile
```

`request.json`, the keychain, and every profile are pre-existing regular files,
owned by `disposable_uid`, mode exactly 0600, link count 1, and on the same
filesystem device (`st_dev`) as the task root. The `profiles` and optional
`profiles/alternates` directories are pre-existing 0700 directories with the
same owner/device/link constraints. Alternate names match
`^[a-z0-9][a-z0-9-]{0,47}\.provisionprofile$`. The three fixed request relative
paths must equal the literal values above; alternates must use only the literal
`profiles/alternates/` prefix. Absolute paths, empty components, `.`, `..`,
backslashes, NULs, non-ASCII names, Unicode normalization variants, and prefix
siblings are rejected.

The request is at most 16 KiB, each profile is at most 1 MiB, all selected and
alternate profiles together are at most 8 MiB, and the dedicated keychain file
is non-empty and at most 64 MiB. Exceeding a cap is
`BLOCKED_PATH_INTEGRITY_CHANGED`; the inspector never reads a keychain database
as ordinary file content.

Path validation is fail-closed and precedes every guarded command:

1. Verify the current account, UID, and home using OS APIs; resolve the home
   once. `--task-root` must be lexically absolute and exactly one descendant at
   the frozen base/run-id depth.
2. Walk with `lstat` every path component from the verified home through the
   target before calling `realpath`. No component may be a symlink. System
   ancestors above the home may be root-owned, but the home and every component
   below it must have the expected disposable owner. The home may be 0700 or
   0750 but may have no group/world write bit or ACL; every task component below
   the home is exactly 0700. ACLs
   are rejected from captured `/bin/ls -lde <exact-path>` metadata. The command
   runs without a shell, its output is capped/redacted, and a parse/exit failure
   blocks before any Keychain command.
3. Resolve home, task root, request, keychain, and profiles with `realpath` and
   prove containment using `path.relative(realTaskRoot, realTarget)`, not string
   prefix comparison. The relative result must be non-empty, must not be
   absolute, and must neither equal `..` nor begin with `../`.
4. Record each target's realpath, `st_dev`, `st_ino`, file type, UID, GID, mode,
   link count, size, and domain-separated path/content digest. Reject hardlinks,
   device/mount crossings, special files, ACLs, and size-cap violations. Apply
   the full ACL/ancestor/device/content check to every selected **and alternate**
   profile, not only the launcher/helper pair. Raw paths never enter the receipt.
5. Open request/profile bytes with `O_RDONLY | O_NOFOLLOW`, compare `fstat` to
   the recorded tuple, enforce the byte cap, and pass profile bytes to
   `security cms -D` on stdin. Do not give profile paths to a child process or
   create decoded intermediate files.
6. Open the dedicated keychain once in the parent with
   `O_RDONLY | O_NOFOLLOW | O_CLOEXEC`; reject the run if any flag is unavailable.
   Before either child starts, require `fstat` to equal the recorded
   `(mode,uid,gid,nlink,size,dev,ino)` tuple and compute a SHA-256 over the opaque
   keychain bytes using positioned reads that do not change the descriptor
   offset. Only the digest survives; buffers are zeroed and contents are never
   parsed, logged, copied, or written. Failure to compute the bounded digest is
   `BLOCKED_KEYCHAIN_CONTENT_IDENTITY_UNVERIFIED`, never a warning.
7. Keep that exact parent descriptor open across both Security commands. For
   each spawn, duplicate it as child fd 3 with
   `stdio: ['ignore','pipe','pipe',keychainFd]`, pass only `/dev/fd/3` as the
   keychain operand, and retain the parent fd until both children have exited
   and final checks finish. The original pathname may not appear in argv,
   environment, cwd, stdin, output, or a fallback. Set child cwd to the separate
   CLI scratch root.
8. Immediately before and after each child, and once after both children,
   repeat `fstat` on the still-open parent descriptor and require the exact
   tuple and positioned-read digest to match. Re-walk the pathname only to
   detect drift; descriptor identity remains authoritative. Any descriptor or
   path drift is `BLOCKED_PATH_INTEGRITY_CHANGED`; never retry or reopen.
9. READY additionally requires the exact installed `security` tool to complete
   both identity and public-certificate commands successfully when `/dev/fd/3`
   is the sole operand. A failure, unsupported descriptor alias, or evidence
   that Security resolves/reopens the original pathname is
   `BLOCKED_KEYCHAIN_DESCRIPTOR_BINDING_UNVERIFIED`. There is no pathname,
   copy, lock, keychain-mutation, or temporary-keychain fallback. Until this
   capability is proved on the real authorized runner/tool build, real inventory
   cannot return READY.

This makes inventory mode normally satisfiable after an operator explicitly
provisions the bounded root, while the unauthorised current slice remains safe:
`tool-only` needs no root, and `inventory` reports
`BLOCKED_TASK_ROOT_MISSING` before any guarded command when the root is absent.

### Guarded inventory phase

Only after the disposable runner and dedicated keychain path pass all
filesystem/user gates may the CLI run:

```text
/usr/bin/security default-keychain -d user
/usr/bin/security find-identity -v -p codesigning /dev/fd/3
/usr/bin/security find-certificate -a -p /dev/fd/3
/usr/bin/security cms -D
/usr/bin/plutil -convert json -o - -
```

Each profile's already-open, `fstat`-verified bytes are sent to `security cms`
on stdin; `plutil` receives the decoded profile on stdin. No profile path is
passed to either child and no intermediate decoded profile or public
certificate is written to disk. `security find-certificate -p` returns public
certificates only. The collector must parse every returned PEM certificate in
memory, compute its SHA-1 fingerprint, and require exactly one certificate whose
fingerprint equals the selected `find-identity` row. All Team/type/issuer/time
checks use that matched certificate, not the mutable identity label. Zero or
multiple matches is `BLOCKED_IDENTITY_PUBLIC_CERTIFICATE_MISMATCH`. The same
matched certificate fingerprint must occur in each selected profile's
`DeveloperCertificates`; the inspector never accepts profile strings alone. It
never asks for or exports a private key.

With `LANG=C` and `LC_ALL=C`, native `find-identity` output is accepted only as
zero or more rows matching exactly
`^  ([1-9][0-9]*)\) ([0-9A-F]{40}) "([^"\r\n]+)"$`, followed by exactly one
summary line `^     ([0-9]+) valid identities found$` and one optional final
newline. Row ordinals must be contiguous from 1, the summary count must equal
the parsed row count, and no prefix/suffix/diagnostic line is allowed. READY
requires the total count to be exactly 1 and that row's label to match
`Developer ID Application: <nonempty name> (<EXPECTED_TEAM_ID>)`. The public
certificate stream may contain other certificates, but exactly one parsed PEM
certificate must have the row's SHA-1 fingerprint; zero or multiple matches
blocks. Labels and summary counts never substitute for that certificate match.

`security default-keychain -d user` is the first guarded Keychain command. It
must exit 0, emit empty stderr, and emit no more than 4096 valid UTF-8 bytes in
exactly one quoted line matching `^"([^"\\\r\n]+)"\n?$`. Escapes, multiple
lines, an empty path, relative path, NUL, or extra text is
`BLOCKED_DEFAULT_KEYCHAIN_UNVERIFIED`. Walk and canonicalize the emitted path
with the same ancestor rules when it exists. The dedicated keychain is rejected
if its canonical device/inode equals the default keychain, if its canonical path
equals the default path, or if it resolves to either conventional
`<verified-home>/Library/Keychains/login.keychain-db` or legacy
`login.keychain`. A missing or unresolvable default-keychain target also blocks;
the inspector may not assume a malformed or absent default is safe. Only after
this check passes may identity or certificate inventory run.

Every process uses stdin `ignore` except the explicit profile-bytes-to-`cms` and
decoded-profile-to-`plutil` pipes, no TTY, no shell, the exact environment
`PATH=/usr/bin:/bin:/usr/sbin:/sbin`, `LANG=C`,
`LC_ALL=C`, `HOME=<verified-disposable-home>`,
`TMPDIR=<verified-task-temp>`, `USER=<verified-disposable-user>`, and
`LOGNAME=<verified-disposable-user>`, captured stdout/stderr, a 5-second
timeout, a 256-KiB combined-output ceiling, and TERM then bounded KILL cleanup.
All other inherited variables are removed. Raw output is never inherited or
logged. A timeout, authorization UI indication, `interaction not allowed`,
locked keychain, or any unexpected output becomes
`BLOCKED_KEYCHAIN_INTERACTION_RISK`; the runner must never unlock, relock, or
change a keychain to continue.

Read-only Keychain commands are still capable of exposing identity labels,
certificate metadata, and private filesystem paths, and a locked or ACL-bound
keychain can request interaction. Therefore:

1. never query the ordinary login/default keychain;
2. never query before proving the current account is the configured disposable
   non-admin user and the explicit keychain is an owner-only, non-symlink file
   outside the login-keychain path;
3. never retry a prompt/locked/interaction result;
4. never execute the inventory phase in a shared interactive user context;
5. require `scutil --nwi` and both `netstat` route-table commands to exit 0 with
   empty stderr and parse successfully. READY requires no reachable non-loopback
   IPv4/IPv6 interface, no IPv4/IPv6 default route, and no non-loopback globally
   routable route. A successful command showing a route is
   `BLOCKED_NETWORK_ISOLATION_MISSING`; a missing, nonzero, truncated, or
   unparseable command is `BLOCKED_NETWORK_ISOLATION_UNVERIFIED`. Silence or a
   nonzero route-table command is never accepted as offline evidence. This check
   precedes any code-signing policy evaluation because platform trust services
   may consult online revocation services;
6. if the implementation cannot prove those guards before the command, stop at
   `BLOCKED_KEYCHAIN_INTERACTION_RISK`.

No command in either phase may contact Apple. Online trust/revocation checks,
`notarytool submit`, `stapler staple`, `codesign -s`, `security import`,
`security export`, `security unlock-keychain`, or any `SecItem`/`SecKey`
mutation are forbidden.

The evaluator constructs one exact row for every check ID in the readiness table:
`{"check_id":string,"outcome":"pass"|"fail"|"not_run","status":null|"BLOCKED_*","blocked_by":null|string,"evidence":object}`.
A failed row has one allowed status and no `blocked_by`; a dependency-skipped
row is `not_run`, has null status, and names an existing failed `check_id` in
`blocked_by`; a passing row has both fields null. Unknown, duplicate, or missing
IDs and invalid dependency graphs are rejected. Rows are sorted
lexicographically by `check_id`, then top-level status is recomputed from all
failed rows using the immutable precedence above. Collector/request input may
not supply status. The redactor independently repeats validation, sorting,
completeness, dependency, and precedence computation and rejects any
caller-provided receipt whose status differs. READY requires every mandatory
row exactly once with `outcome=pass`; no `not_run` is allowed. Reordering,
deleting a failure, injecting READY, or attaching a lower-precedence status must
fail. Unknown conditions become `BLOCKED_INVENTORY_FAILURE`, never READY. A
minimal leak-safe receipt is written for the first two statuses; it contains no
captured inventory.

`redacted_inventory` may contain only OS/CLT/tool versions and digests,
architecture, boolean presence/counts, certificate validity times, profile
validity times, public bundle IDs/access-group suffix, the domain-separated task
root digest, `operator_cleanup_required`, and other domain-separated digests. It
may not contain raw account, identity, user, path, or profile data.

Required non-claims are fixed:

1. no signing or private-key operation was performed;
2. no identity, certificate, profile, keychain, or Apple account was changed;
3. no Secure Enclave or generic-password item was created/read/changed/deleted;
4. no notarization, Gatekeeper, online revocation, portal, browser, provider, or
   network request was performed; local route-table inspection is not an online
   verification;
5. no product, native helper, manifest, lockfile, migration, ledger, Git history,
   push, deploy, or live system was changed;
6. READY means ready to attempt the separately authorized proof, not M3.01/M3.03
   acceptance.

## Cleanup contract

The CLI creates at most one `mkdtemp` directory named
`skillmap-m303-apple-readiness-*` under the OS temp directory, mode 0700. Any
request/profile/certificate/command bytes are held in memory; if a test adapter
must use a temporary file, it is mode 0600, contains synthetic data only, and is
removed in `finally`. Zero mutable buffers after parsing where practical. Never
delete any pre-existing path. Cleanup failure is
`BLOCKED_INVENTORY_FAILURE`, not a warning.

No cleanup may run a broad recursive delete, glob, unresolved environment
variable, or home/workspace root. The exact task temp path must be captured at
creation, checked to be inside `os.tmpdir()` with the exact prefix, and removed
only after all children exit. Post-cleanup must prove no matching task process,
listener, temp directory, keychain/profile/certificate file, or repo residue.
The scratch cleanup must also prove it never resolved equal to, above, or below
the operator task root. Inventory mode never deletes or changes the task root,
request, keychain, profiles, base directory, or their metadata. A later
authorized operator owns their exact cleanup; this readiness slice reports the
task-root digest and `operator_cleanup_required: true` without exposing its path
or attempting cleanup.

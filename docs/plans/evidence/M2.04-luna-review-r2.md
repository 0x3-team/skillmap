## Independent contract review

### M1.03 and M1.05 traceability

The version table stores exact manifest bytes as `bytea`, bounded canonical metadata, qualified source, provenance, analysis adjunct state, and checked SHA-256 manifest/content digests (`migration:10-123`). The immutability trigger rejects updates to identity, account/skill binding, canonical bytes, digests, metadata, source, provenance, analysis state, and creation time (`migration:125-163`). Same-account/same-Managed-Skill manifest and content digest uniqueness is enforced while equal content remains legal across skills and accounts (`migration:34-46`; `test:271-343`). This correctly treats the M1.03 canonical projection and M1.05 digest as upstream authority without JSON reserialization or a second digest algorithm.

The SQL boundary does not attempt to implement M1.04 file/path admission or M1.03 file-entry storage. That work belongs to M2.05, which is absent. The stored `manifest_projection` is bounded and opaque; the accepted M1.03 vectors remain the canonical serialization proof (`acceptance:86-90`).

### M1.06 lifecycle and release-binding semantics

Lifecycle is on `private.managed_skill_releases`, not immutable versions or the Managed Skill aggregate (`migration:216-269`). All nine exact M1.06 states are checked, eligibility reasons are bounded, sorted, duplicate-free syntax-only codes, and active releases require empty reasons (`migration:246-268`). The transition trigger implements the frozen legal graph and blocks any selected active release from becoming non-active, newly revoked, or newly ineligible until its pointer is removed (`migration:331-377`). Timestamp ownership and monotonicity are enforced as described above. The focused test checks the vocabulary, illegal transition, binding immutability, eligibility shape, and selected-release safety (`test:389-439,547-612`).

This migration deliberately does not invent an analysis/review vocabulary or make the aggregate lifecycle authoritative. Eligibility is a bounded relational gate for this phase; future M2.10 mutation functions must enforce the full M1.06 authority and evidence guards.

### M2.02 ordering, constraints, and function boundary

The frozen order is respected: immutable versions and their trigger come first, release bindings and lifecycle trigger next, then the Managed Skill pointer/revision and composite same-account/same-skill FK, then durable receipts and activation functions (`migration:10-163,216-424,440-451,453-861`). The composite foreign keys prevent cross-account and cross-Managed-Skill binding, while `activation_revision >= 0` and the scoped receipt uniqueness enforce the CAS/idempotency shape (`migration:34-46,230-243,448-482`).

The API takes no account argument and derives ownership from `auth.uid()` (`migration:499-541`; `test:175-183`). Missing, foreign, malformed-at-the-boundary, noneligible, stale, and conflicting requests fail closed without pointer mutation. A same-key/same-input replay returns the stored result; any input mismatch raises the bounded conflict path without rewriting the prior receipt (`migration:548-569`). The conflict path is intentionally not a new result state: M2.02 owns its future `IMPORT_REPLAY_CONFLICT` public mapping, while the private activation result states remain exact and closed.

### Locking, CAS, replay, and concurrency

The function takes the account advisory lock first (`migration:543-546`), then locks the Managed Skill (`migration:571-586`), then the immutable version and mutable release in the M2.02 version-before-release order (`migration:613-695`). It increments the aggregate revision exactly once only when the selected release changes (`migration:777-807`). The focused autonomous dblink race proves both expected-revision-zero calls commit bounded decisions, one wins `active`, one returns `VAULT_STALE_REVISION`, the revision is `1`, the winning pointer matches the active result, and there are exactly two receipts (`test:660-862`). No external storage, network, queue, filesystem, or provider operation is present under these locks.

Rollback is selection of another already-eligible release and leaves both immutable versions unchanged (`test:509-528`). The migration is one transactional forward migration (`migration:1-8,863`); the test transaction rolls back synthetic fixtures and the autonomous race explicitly commits cleanup before disconnect (`test:660-663,864-881`). Post-commit repair remains forward-only under M2.02.

### ACL/RLS and catalog isolation

All new canonical tables force RLS, start with zero policies, and revoke application-role access (`migration:165-168,426-429,484-492,856-861`). The focused test checks both version/release tables, the receipt table, the exact API function, and the security-definer boundary (`test:138-183,883-889`). The API function remains inert to application roles in this phase. The hosted-catalog regression remains `97/97`, its security-definer allowlist contains the exact activation name only (`hosted_catalog_rls.test.sql:52-70`), and the catalog views/current-version authority remain untouched (`focused test:185-200`).

The temporary `postgres` ownership is bounded: both security-definer activation functions are ungranted and therefore unreachable by application roles (`migration:819-854`). M2.10 must, in one atomic transaction, add the exact owner policies—including the receipt-table policy needed by the function under forced RLS—transfer both the private implementation and API wrapper owners to `skillmap_vault_definer`, map all public failures through the accepted M2.02 registry, and grant only the reviewed execute path last. No current M2.04 exposure is present.

### Scope and rollback boundary

The migration adds only immutable versions, release bindings/lifecycle, the aggregate pointer/revision, receipts, triggers, and the ungranted activation primitive. It creates no file records, blob references, storage objects/policies, import sessions, routing decisions, feedback, device records, catalog `current_version_id` mutation, or public grants (`migration:5-8,440-453,856-861`). The candidate therefore does not leak M2.05 or later scope. The catalog test hash is unchanged from R1 and the supplied regression remains `97/97`.

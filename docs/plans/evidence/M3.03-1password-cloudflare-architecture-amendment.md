## Decisive architecture

### What 1Password replaces

Google Cloud Secret Manager and its proposed service account, regional secret,
versions, IAM grants, destroy proof, and audit lane are removed completely.
1Password becomes the only approved human-operated escrow for long-lived
**control-plane recovery material**, such as a dedicated Cloudflare rotation
API token recovery copy, its revocation/runbook metadata, and support-case
references. The normal rotation runtime does not call 1Password.

There is no independent replay-key escrow in this design. Losing an in-window
Cloudflare epoch key causes the affected refresh family to be revoked and
re-paired; it does not trigger restoration or reconstruction. This availability
tradeoff is necessary to preserve the destruction bound.

### What 1Password cannot replace

1Password is a secret vault, not an Apple code-signing authority or a macOS
entitlement issuer. It cannot provide:

- Developer ID Application identity or secure timestamp;
- notarization, stapling, or Gatekeeper acceptance;
- an Apple Team ID, explicit App IDs, provisioning profiles, or a restricted
  `keychain-access-groups` entitlement;
- Secure Enclave P-256 generation or a non-exportability guarantee; or
- a trustworthy signed-launcher/helper caller identity.

Storing a private key in 1Password would make it retrievable by an authorized
client. It would not turn the key into a Secure Enclave key.

### First binary gate — unsigned/ad-hoc Data Protection Keychain capability

No Keychain storage design is selected yet. Before a V3 contract, helper, or
support label is authored, Luna High may implement one non-product capability
spike using public/synthetic canaries only. It must test two binaries built from
the exact same reviewed Swift source:

1. an actually unsigned executable; and
2. an ad-hoc-signed executable, with no Developer ID identity.

Both rows must have no provisioning profile, no Team ID, no entitlement file,
no `keychain-access-groups`, and no `kSecAttrAccessGroup`. The receipt must bind
the source, compiler/toolchain, unsigned binary, ad-hoc binary, signature state,
entitlement output, architecture, OS/build, executable path/mode, and hashes.
An ad-hoc signature is integrity metadata only and is not caller identity.

Each row performs the same exact lifecycle against a unique disposable item:

- `kSecClassGenericPassword`;
- `kSecUseDataProtectionKeychain = true`;
- `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`;
- `kSecAttrSynchronizable = false`;
- no access-group key at all;
- random synthetic service/account names under a proof-only prefix; and
- random synthetic value bytes that never enter durable evidence.

The lifecycle is add, exact copy-and-byte-compare in private memory, update,
exact second copy-and-compare, delete, and post-delete `errSecItemNotFound`.
It also proves duplicate-add behavior, wrong-account denial, no synchronizable
copy, no unexpected UI, no argv/environment/stdout/stderr/file/log/crash
leakage, and exact cleanup. The spike records only fixed OSStatus names/numbers,
digests, lengths, booleans, and redacted timing. It does not create a product
device key or refresh token and does not test product login.

The spike result is binary:

- `PASS_DP_KEYCHAIN_NO_PROFILE_CAPABILITY` requires every lifecycle and
  redaction assertion to pass for **both** unsigned and ad-hoc rows on the exact
  target configuration; or
- `FAIL_DP_KEYCHAIN_NO_PROFILE_CAPABILITY` applies to any other result,
  including `errSecMissingEntitlement` (`-34018`), row divergence, prompt,
  partial cleanup, or an unclassified OSStatus.

On PASS, this plan permits a later Sol-owned amendment slice to select and
freeze V3 semantics using the observed capability. PASS is capability evidence,
not product custody acceptance. On FAIL, stop and return to GPT-5.6 Sol Max
planning. Do not remove `kSecUseDataProtectionKeychain`, add a profile or access
group, move the value to a file, use the ordinary login Keychain, or store the
connector credential in 1Password inside the execution turn.

Honest fallback candidates for that future planning turn are:

- an ordinary login-Keychain item with
  `kSecUseDataProtectionKeychain` omitted, with its own lock/headless/export and

- an owner-only file-based credential store, with an explicit encryption-key,

If the spike fully passes and a later Sol plan freezes V3, the likely private-
preview tradeoff remains exportable software P-256 custody in a local Keychain
record, no trusted caller identity, no provisioned access group, and no public
distribution claim. The exact record service/account/schema, helper operations,

The security downgrade would still be explicit: malware or another process
running as the same logged-in user may invoke or extract the connector
credential. Least-lived access tokens, server proof nonces, family/key
revisions, remote revoke, non-sync attributes, and residue tests mitigate but
do not recreate hardware custody or non-exportability.

## Replay-key material decision

The replay contract uses independent random 32-byte AES keys for five-minute
epochs. Logical replay remains strict before `response_issued_at + 600s`.
Each key must become unrecoverable no later than `epoch_end + 930s`; because an
epoch is 300 seconds, the maximum bound from epoch start remains 1,230 seconds.

| Material in 1Password | Decision | Reason |
|---|---|---|
| One item/version per epoch key | **Forbidden** | Every update creates recoverable item history; deleted items are recoverable for 30 days; 1Password documents daily server backups. These exceed 930/1,230 seconds. |
| A replay wrapping/root/derivation key | **Forbidden** | It would reconstruct or decrypt expired epoch keys and directly contradict the accepted independent-random/no-retained-root property. |
| A recovery bundle containing recent epoch keys | **Forbidden** | Item history, deletion recovery, backups, clients, and any Connect cache make the truthful recoverability bound longer or unknown. |
| Cloudflare rotation management token | **Allowed with conditions** | It is control-plane recovery material, not a replay decryption key. The token must be dedicated, least-privilege, provider-revoked before an old 1Password version is treated as inert, and never available to the consumer Worker. |
| Runbook, resource digests, support case reference | **Allowed** | These contain no replay secret and do not alter cryptographic exposure. |

The documented service-account example limits—1,000 writes/hour, 10,000
reads/hour, and 50,000 account read/write operations/day—would not by
themselves prevent twelve rotations per hour. Quota fit is irrelevant because
retention fails the security contract. Connect's lack of request quotas also
does not solve upstream item history/backups, and current queried documentation
did not provide a deletion/cache-erasure bound. Neither service accounts,
Connect, Secrets Automation, `op run`, `op read`, nor `op inject` belongs in the
replay runtime.

For human recovery, prefer 1Password desktop/CLI integration. Do not use
`op run` environment injection, `op read` stdout, or `op inject` files for the
rotation token. If a later automation lane needs a 1Password service account,
it requires a separate threat review because the service-account token itself
becomes a long-lived machine credential.

## Cloudflare runtime choice

### Selected candidate: Secrets Store, three fixed epoch slots

Cloudflare Workers per-Worker secrets are rejected for replay keys. Current
Workers documentation says `secret put` and `secret delete` create a new Worker
version and deploy it immediately; version rollback and old-version semantics
make this a deployment lifecycle, not a five-minute destruction primitive.

Cloudflare Secrets Store is the sole candidate runtime because it provides
account-level, Workers-scoped, write-only secret values that can be bound to a
Worker without putting values in source or Wrangler `vars`. Current public docs
state open-beta limits of one store per account, 100 production secrets per
account, and 1,024 bytes per value. `Account Secrets Store Edit` is required to
create, edit, delete, and bind secrets; no per-secret edit permission is
documented.

Use three fixed secrets/bindings, not one read-modify-write JSON ring:

```text
DEVICE_AUTH_REPLAY_SLOT_0
DEVICE_AUTH_REPLAY_SLOT_1
DEVICE_AUTH_REPLAY_SLOT_2
```

At the start of epoch `E`, an isolated rotation controller generates one random
key in private memory and overwrites slot `E mod 3` with a strict payload
containing only schema, numeric `epoch_id`, and canonical key bytes. The
consumer Worker validates all three payloads, selects exact `epoch_id`, and
never tries another epoch key after an AEAD failure.

Three slots are sufficient: the latest possible response in an epoch loses its
600-second replay eligibility before that slot is reused 900 seconds after the
epoch starts. Slot overwrite therefore begins 600 seconds after epoch end and
leaves 330 seconds for confirmed propagation before the
`epoch_end + 930s` destruction deadline. If a new value has not propagated,
refresh fails closed as `temporarily_unavailable`; it never uses a stale slot
for a new epoch.

The controller is a separate scheduled Cloudflare surface with no database,
Supabase credential, consumer route, or secret-read binding. Controller code
hard-allows only the exact account digest, store digest, and three slot IDs and
names, but this code allowlist is not represented as provider IAM: `Account
Secrets Store Edit` can affect the account's Secrets Store. The provider blast
radius must therefore be made structurally true before a token exists.

### Account/store and controller-token blast-radius gate

Run a read-only inventory under separate authorization before creating any
controller token or secret. Bind the exact account ID and store ID as
domain-separated digests; enumerate every secret's ID, name, scope, comment,
state, and Worker/AI binding without reading values; enumerate every Worker
using the store; and record existing token/role and audit visibility. The
selected account/store must contain no unrelated Secrets Store material. Its
only permitted production secret records are the three SkillMap replay slots.
If any unrelated secret or binding exists, stop and either select a dedicated
account after a new Sol plan or reject Secrets Store; do not move, rename,
overwrite, or delete the unrelated material.

The controller token must be a dedicated API token whose resource clause names
the exact Cloudflare account and whose only permission is `Account Secrets
Store Edit`. It must not have Workers Scripts Edit, Workers Routes Edit,
Account Settings, membership, billing, DNS, Access, Logs, or any unnecessary
deployment permission. Deploying or updating controller code uses a separate,
time-bounded operator/CI authority; the runtime rotation token cannot create,
deploy, version, route, roll back, or delete a Worker. The controller still
checks the exact account/store/slot allowlist before every write and treats an
unexpected inventory result as a kill condition.

A recovery copy of the rotation token may be held in 1Password. The provider
token must be revoked before an older 1Password item version is treated as
inert. Application allowlisting, an isolated account/store, audit review, and
a kill switch are compensating controls; the plan does not describe the token
itself as narrow to three secrets.

Before private preview, test normal revocation and assumed compromise with a
non-production token: disable the schedule, revoke the exact token through an
independent administrator credential, prove the old token receives a fixed
authorization denial, mint a replacement only after inventory revalidation,
replace every slot with fresh random material, and scan audit logs for writes
from first possible compromise through revocation. A compromise response also
stops refresh/pairing and revokes every disposable/new family whose replay
ciphertext could have been sealed under an attacker-known slot. Failure to
identify the affected interval or to prove old-token denial rejects the
controller design.

### New-value visibility and private-preview availability gate

Fail-closed behavior prevents stale-key use but can make refresh unavailable
while an overwrite propagates. Old-value erasure and new-value availability are
separate acceptance dimensions. Measure new-value visibility from the
successful Secrets Store update response's monotonic timestamp until the exact
new `epoch_id` is observed by every configured probe, including already-running
and fresh isolates from at least two geographically distinct vantage points.

The non-production provider proof must cover at least 288 consecutive
five-minute rotations, controller restarts, slot wraparound, API timeouts, and
fresh/existing-isolate reads. The explicit private-preview threshold is:

- p99 new-value visibility no greater than 5 seconds;
- no observed visibility time greater than 15 seconds;
- no more than 15 consecutive seconds of rotation-attributable
  `temporarily_unavailable` in any epoch; and
- zero synthetic refresh operations exhausting a bounded 20-second retry
  budget across the 288-rotation run.

The consumer must report `temporarily_unavailable` and a bounded retry hint
during the gap; it must not read a stale epoch, extend token expiry, or fall
back to another slot. Any threshold miss blocks private preview even if the
old-value erasure bound passes. A later production SLO requires a separate
decision and cannot be inferred from this private-preview threshold.

### Retention evidence gate

Public Cloudflare documentation confirms create/edit/delete, binding, audit,
and quota surfaces. It does **not** state an account-applicable maximum for old
values after overwrite/delete, replica/backup/DR/support recovery, propagation
to all locations, values already materialized in running isolates, cache
eviction, or permanent deletion. Those semantics are `unknown`, not inferred.

Send this support inquiry before any production decision:

> SkillMap is evaluating Cloudflare Secrets Store for three fixed cryptographic
> epoch-key slots. One slot is overwritten every five minutes and read through
> Workers Secrets Store bindings. For our account and plan, please provide the
> maximum time after an overwrite or delete during which the old value can
> remain decryptable or readable from any replica, backup, snapshot,
> disaster-recovery system, support tool, soft-delete state, binding/platform
> cache, or already-running isolate. Please state propagation/consistency
> semantics across all locations, whether and how active isolates are forced to
> discard old binding values, whether the customer or Cloudflare can recover an
> overwritten/deleted value, audit events and retention, API rate limits for
> twelve writes per hour, and whether edit permission can be restricted to
> three named secrets. Our acceptance requires the old slot value to be
> unrecoverable everywhere no later than 930 seconds after its epoch ends; the
> planned overwrite begins 600 seconds after epoch end, leaving at most 330
> seconds for propagation and erasure. Please also state the maximum time for
> a newly acknowledged value to become visible to fresh and already-running
> isolates in all locations, because private preview separately requires p99
> visibility within 5 seconds and a measured maximum within 15 seconds. Please
> identify any open-beta, SLA, or contractual limitation and the controlling
> document or contract.

Required receipt: case ID, sent-at, account digest, exact request hash,
responder/source, full response and attachment hashes, and an independent
security verdict. Do not retain account name, email, token, or secret values in
the repo receipt.

No production replay key, slot value, controller token, production binding, or
production scheduler may be created until the written answer unambiguously
covers every surface above with a maximum within the bound and an independent
review accepts it. An API `deleted` status, audit event, dashboard disappearance,
or empirical fresh-isolate failure is supporting evidence only.

If Cloudflare gives a longer, conditional, beta-only, or unknown bound, reject
this runtime choice. Do not weaken the bound inside implementation. A new
M1.08/M3.02 risk amendment and explicit user acceptance would be required to
continue with a longer truthful exposure.

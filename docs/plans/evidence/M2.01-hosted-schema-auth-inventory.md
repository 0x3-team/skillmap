## 2. Existing hosted source of truth

### 2.1 Schemas, exposure, and catalog authority

The hosted database has two deliberately separated schemas. `api` is the only schema exposed through PostgREST; `private` is canonical catalog and audit truth and is not exposed through PostgREST (`supabase/migrations/20260711192500_hosted_catalog_foundation.sql:3-10`). This boundary is the primary reuse decision for M2: managed-skill data must not be added to the public catalog tables merely because both domains contain a skill-shaped object.

The existing catalog authority is:

- `private.publishers` and `private.publisher_members` for publisher identity and membership (`supabase/migrations/20260711192500_hosted_catalog_foundation.sql:54-76`).
- `private.source_repositories` for canonical GitHub source identity and publication state (`supabase/migrations/20260711192500_hosted_catalog_foundation.sql:78-93`). The cited authority is GitHub-specific; Gitea parity remains unverified by M2.01.
- `private.skills` for public catalog skill identity, publisher/repository ownership, public/lifecycle state, and a catalog-only `current_version_id` pointer (`supabase/migrations/20260711192500_hosted_catalog_foundation.sql:95-124`, `supabase/migrations/20260711192500_hosted_catalog_foundation.sql:244-248`).
- `private.skill_versions` for immutable public catalog version coordinates, manifest/evidence/grade metadata, publication state, and catalog artifact coordinates (`supabase/migrations/20260711192500_hosted_catalog_foundation.sql:126-242`).
- `private.skill_relationships` for catalog-version relationships (`supabase/migrations/20260711192500_hosted_catalog_foundation.sql:250-262`).
- `private.audit_events` for append-oriented audit subjects and payloads (`supabase/migrations/20260711192500_hosted_catalog_foundation.sql:264-272`, with later subject-type/idempotency extensions at `supabase/migrations/20260713003000_launch_safety_reports_lifecycle.sql:3-10`).
- `api.catalog_skill_versions`, `api.catalog_skills`, and `api.catalog_skill_relationships` as security-invoker, security-barrier public projections (`supabase/migrations/20260711192500_hosted_catalog_foundation.sql:470-610`).
- `api.saved_skill_catalog` as the owner-filtered saved-bookmark join over `api.saved_skills` and the public catalog projection (`supabase/migrations/20260711192500_hosted_catalog_foundation.sql:612-619`).

The catalog current-version pointer is structurally constrained to a row in `private.skill_versions` belonging to the same catalog skill (`supabase/migrations/20260711192500_hosted_catalog_foundation.sql:244-248`). It is therefore catalog publication authority, not a candidate pointer for managed activation.

### 2.2 Profiles, saved bookmarks, submissions, and reports

`api.profiles` is the minimal account profile identity: `user_id` references `auth.users` with cascade deletion and `created_at` is server-owned (`supabase/migrations/20260711192500_hosted_catalog_foundation.sql:274-277`). `api.saved_skills` is a user-owned bookmark relation to `private.skills(public_id)` with a `(user_id, skill_id)` primary key (`supabase/migrations/20260711192500_hosted_catalog_foundation.sql:279-284`). It is a catalog bookmark relation, not a managed-skill identity or release relation.

The existing submission/report domain is reusable only for its existing public-catalog submission workflow:

- `api.skill_submissions` and its private receipt/worker/audit relations are the source-import submission queue and operator evidence authority. The lifecycle, completion, worker claim, provider deferral, and evidence-authority migrations are the existing source of truth; service-role-only functions are explicitly gated in the migration and pgTAP corpus.
- `api.skill_reports` records authenticated reports against an exact public catalog skill/version and has bounded idempotency, state, disposition, and resolution fields (`supabase/migrations/20260713003000_launch_safety_reports_lifecycle.sql:12-58`).
- `private.enforce_skill_report_insert()` requires verified authenticated ownership, bounded message/rate limits, and an exact currently public, publisher-authorized catalog version (`supabase/migrations/20260714050000_report_authorization_enforcement.sql:7-68`).
- `api.my_skill_reports` is the authenticated owner-RLS report-history projection and exposes the opaque idempotency key only to the owner (`supabase/migrations/20260715020000_hosted_report_idempotency_recovery.sql:8-21`).

Managed imports, managed versions, and managed releases must not be inserted into `api.skill_submissions`, `api.skill_reports`, `api.saved_skills`, or the public catalog relations as a shortcut. M2.02 must reserve separate managed authorities and explicit compatibility projections.

## 3. Auth, claims, clients, and path boundaries

### 3.1 Auth identity and verified claims

The server and browser clients use the publishable Supabase key, set the database schema to `api`, and rely on Supabase session cookies/claims rather than a service-role key (`apps/web/lib/supabase/server.ts:1-29`; `apps/web/lib/supabase/browser.ts:1-16`). Server account actions call `supabase.auth.getClaims()` and classify the result through `classifyVerifiedClaims`; an unverified or unavailable result is not treated as authenticated (`apps/web/app/account/data-actions.ts:56-67`; `apps/web/app/account/export/route.ts:12-27`; `apps/web/lib/auth/account-state.server.ts:8-16`).

The database ownership predicates use `auth.uid()` and require the caller's row owner to equal the verified caller identity. The report insert trigger rejects non-authenticated callers, null caller IDs, or reporter IDs that differ from `auth.uid()` (`supabase/migrations/20260714050000_report_authorization_enforcement.sql:14-18`). Submission abuse enforcement applies the same owner rule (`supabase/migrations/20260713003000_launch_safety_reports_lifecycle.sql:67-75`). These are reusable patterns for M2.02 RLS and security-definer wrappers.

“Verified claims” means the application has accepted the Supabase claim result through the existing classifier. It does not mean an arbitrary browser-supplied `user_id`, email, or profile row is trusted. No M2 design may authorize by a client-provided account identifier.

### 3.2 Client and API exposure inventory

| Surface | Current authority | M2 implication |
| --- | --- | --- |
| Server Supabase client | `createSupabaseServerClient()`; cookie-aware SSR client, `api` schema | Reuse for authenticated dashboard/account reads; keep service-role operations out of browser/server-component clients. |
| Browser Supabase client | `createSupabaseBrowserClient()`; publishable key, `api` schema, session-aware | Reuse only for RLS-protected `api` projections and owner actions. Never expose `private` or service-role credentials. |
| Public catalog client | `createPublicCatalogClient()`; no session persistence, bounded fetch, `api` schema | Reuse for anonymous public catalog reads only. It must not query managed-private projections. |
| API routes/actions | Existing account, catalog, submission, report, and auth callback routes | Extend through new explicit managed routes/actions only after M2.02 contracts; do not overload public catalog routes. |
| Private schema | No PostgREST exposure; security-definer/internal worker authorities only | Managed base tables and worker evidence belong here unless a reviewed `api` projection is explicitly required. |

`safeNextPath()` rejects external origins, protocol-relative paths, backslashes, control characters, and decoded traversal forms (`apps/web/lib/auth/paths.ts:1-24`). This helper and equivalent canonical path validation are reusable for import/session status paths and callback continuations.

## 6. Non-confusion proof and namespace rules

The following distinctions are mandatory acceptance invariants for M2.02:

1. **Catalog skill IDs** identify public publisher/repository catalog skills (`skl_…`) in `private.skills`; **managed skill IDs** identify account-owned personal skills in a separate namespace and table. Equal-looking strings are not sufficient proof of equal identity.
2. **Catalog version IDs** identify public catalog versions (`skv_…`) in `private.skill_versions`; **managed version IDs** identify immutable personal versions in a separate namespace/table. A catalog version is not a managed version merely because both have a manifest or digest.
3. **Saved bookmark IDs/rows** are relations from an account to public catalog skill IDs in `api.saved_skills`; they are neither managed skill identities nor release bindings. The existing `api.saved_skill_catalog` join is a public-catalog projection only.
4. **Managed activation/release IDs** identify personal release decisions and must not be represented by or derived from `private.skills.current_version_id`. That pointer remains catalog-only and is protected by the catalog skill/version foreign key (`supabase/migrations/20260711192500_hosted_catalog_foundation.sql:244-248`).
5. **Public catalog queries cannot return personal managed rows.** Existing public views read the private catalog tables with explicit publisher/repository/publication/license/revocation/quarantine/current-version predicates (`supabase/migrations/20260711192500_hosted_catalog_foundation.sql:470-610`). Managed tables are not joins in those views; M2.02 must preserve that non-join and prove it with negative RLS/projection tests.
6. A routing decision may select either a public catalog candidate or a managed release only through a typed contract branch. It must not coerce IDs by prefix stripping, table union, or shared mutable “current version” fields.

## 7. Auth boundary diagram in prose

Anonymous browser requests can read only the intentionally public `api` catalog projections through the publishable-key client and public grants. They cannot read profiles, owner relations, managed tables, private audit data, or service-role functions.

An authenticated browser carries a Supabase session cookie/JWT. The server validates claims with `getClaims()` and the existing classifier, then calls only `api` objects whose RLS predicates bind rows to `auth.uid()`. Browser code never receives a service-role credential and never selects `private` directly.

An authenticated device/connector is a separate M1/M3 boundary: it presents the reviewed device-auth contract and receives only the selected immutable bundle/decision permitted by the API. It is not an operator and cannot mutate managed storage or catalog authority by possessing a public ID.

The worker is a server-side service-role actor constrained by exact-version RPC wrappers and private functions. Worker authority is not equivalent to account ownership; all worker inputs must carry an account/session or import authority established by a server-side function.

The operator is a separately authorized human/control-plane actor. Existing dual-control and service-role gates protect catalog publication/disposition; those authorities must not be granted to ordinary authenticated users or repurposed for personal managed-skill writes.

The service role bypasses ordinary RLS only inside explicitly reviewed security-definer/RPC boundaries. It is not a browser role, not a user identity, and not an acceptable substitute for owner predicates.
